# [객체지향프로그래밍(JAVA)] 객체지향프로그래밍 학습 (5) - `클래스`는 문법이 아니라 설계의 최소 단위였다

같은 스마트폰 모델인데도 내 폰과 다른 사람 폰은 상태가 다르다. 배경화면도 다르고, 볼륨도 다르고, 저장된 연락처도 다르다.

그런데 이름은 같은 기종이다.

이번 5주차 `객체지향프로그래밍(JAVA)` 교안을 읽으면서 계속 떠오른 장면이 바로 그거였다. `클래스`를 설명할 때 흔히 설계도나 틀이라고 말하는데, 이번에는 그 비유가 꽤 현실적으로 들어왔다.

지금까지는 자바 문법을 배우면서 변수와 연산, 제어문 같은 조각을 익히는 느낌이 강했다. 그런데 `클래스`가 등장하니 코드가 갑자기 덩어리로 보이기 시작했다.

무엇을 저장할지, 무엇을 할 수 있는지, 어떤 이름으로 묶을지 한 자리에서 설명되기 때문이다. 문법을 하나 더 배우는 기분이 아니라, 코드가 왜 더 사람답게 읽히는지 이유를 배우는 시간에 가까웠다.

## `클래스`를 배우면 코드가 값의 묶음이 아니라 대상처럼 보인다

교안에서 `SmartPhone` 예시를 중심으로 `속성`과 `메서드`를 함께 보여 주는 부분이 특히 좋았다.

`color`, `size`, `volume` 같은 값이 있고, `call()`, `volumeUp()`, `volumeDown()` 같은 동작이 있다. 이걸 한데 모아 놓으니 스마트폰이라는 대상이 코드 안에서 제법 선명하게 살아난다.

예전에는 코드가 숫자와 문자열, 함수 호출의 모음처럼 보였다면, `클래스`를 배우고 나서는 "무엇에 대한 코드인지"가 더 빨리 읽힌다. 이 점이 생각보다 중요했다.

프로그램은 결국 현실의 무언가를 모델링하는 일인데, `클래스`는 그 모델링을 시작하는 가장 작은 단위처럼 느껴졌기 때문이다.

### `속성`과 `메서드`를 같이 봐야 대상이 완성된다

스마트폰을 스마트폰답게 만드는 건 외형 이름만이 아니다. 색상과 크기 같은 `속성`도 필요하고, 전화를 걸고 볼륨을 올리는 `동작`도 필요하다.

교안이 이 둘을 한 클래스 안에 같이 두는 이유도 결국 여기에 있다. 상태와 행동이 함께 있어야 코드가 하나의 대상을 설명하기 쉬워진다.

실제로 이 구조를 보고 나니, `클래스`는 데이터를 예쁘게 정리하는 상자라기보다 **데이터와 행동을 한 책임 아래에 묶는 방식**처럼 느껴졌다. 그래서 같은 대상과 관련된 기능을 어디에 두어야 할지도 조금 더 명확해진다.

### `클래스`는 비슷한 코드를 반복하지 않게 만드는 장치이기도 했다

객체지향 설명을 들으면 자꾸 추상적인 설계 이야기만 떠오르는데, 사실 `클래스`가 주는 효용은 꽤 현실적이다. 같은 구조를 가진 대상을 여러 개 다뤄야 할 때, 속성과 동작을 매번 따로 적지 않아도 된다.

예를 들어 스마트폰을 두 대, 세 대 만들어야 한다고 해서 `color1`, `color2`, `volume1`, `volume2`처럼 값을 흩어 놓기 시작하면 코드는 금방 읽기 어려워진다.

`클래스`는 그 반복을 한 번의 정의로 모아 두고, 각 객체가 자기 상태만 따로 가지게 해 준다.

그래서 `클래스`는 설계 개념이면서 동시에 중복을 줄이는 구조이기도 하다. 교안 속 예시가 단순해 보여도 오래 남는 이유는, 코드가 왜 묶여 있어야 하는지를 아주 기본적인 수준에서 설득해 주기 때문이다.

#### 이름을 붙이는 방식에도 이미 설계 감각이 들어 있다

교안에서 클래스 이름은 대문자로 시작하는 영문 이름을 사용한다고 짚는 부분도 그냥 스타일 가이드처럼 지나치기 어려웠다. 이름 규칙이 있다는 건, 코드를 읽는 사람이 이 대상을 한눈에 구분할 수 있게 하려는 약속이기 때문이다.

결국 객체지향은 문법을 아는 것만큼, 읽히는 구조를 만드는 태도와도 맞닿아 있다는 생각이 들었다.

## `인스턴스 생성`은 틀을 실제 대상으로 꺼내 오는 순간이다

클래스를 알았다고 해서 바로 동작하는 건 아니다. 교안에서 `인스턴스 생성`을 따로 강조한 이유도 여기 있다.

`클래스이름 참조변수 = new 클래스이름();`라는 문장이 중요한 건, 설계도 수준에 있던 개념이 실제 메모리 안의 대상으로 바뀌는 지점을 보여 주기 때문이다.

### `참조변수`는 단순한 문법이 아니라 대상에 닿는 손잡이 같다

`sp.color`, `sp.call()`처럼 `참조변수`를 통해 속성과 메서드에 접근하는 장면을 보면, 객체는 그냥 생성되는 걸로 끝나지 않는다는 사실이 분명해진다. 생성된 객체와 실제로 상호작용하려면 그것을 가리키는 이름이 필요하다.

그 이름이 바로 `참조변수`다.

이 부분이 중요하게 느껴진 건, 객체를 다룬다는 게 변수값 하나를 불러오는 것과는 다른 감각이기 때문이다. 색상값만 따로 들고 있는 게 아니라, 스마트폰이라는 대상 전체에 접근하는 셈이다.

그래서 `참조변수`를 이해하면 코드가 개별 값 중심에서 객체 중심으로 조금씩 이동하는 느낌이 든다.

### 같은 `클래스`로 만든 `인스턴스`가 왜 서로 다른 상태를 가질까

교안의 `sp1`, `sp2` 예시는 아주 기본적이지만 오래 남는다.

둘 다 같은 `SmartPhone` 클래스에서 만들어졌지만, `sp1.color = "Gold"`, `sp2.color = "Black"`처럼 서로 다른 상태를 가질 수 있다.

그리고 `sp1.volumeUp()`을 호출해도 `sp2.volume`은 그대로 남아 있다.

이 장면이 좋았던 이유는 `클래스`와 `객체`의 차이를 가장 단순하게 보여 주기 때문이다. 클래스는 공통 구조이고, 객체는 그 구조를 바탕으로 각각 독립적으로 존재하는 실체다.

같은 틀에서 태어났지만 서로 다른 값을 가지는 순간, 객체지향이라는 말이 훨씬 덜 추상적으로 느껴진다.

#### 설계도는 하나여도 실제 대상은 여러 개일 수 있다

현실에서도 자동차 모델은 하나지만 실제 차량은 수없이 많다. 각 차량마다 주행거리와 연료량이 다르다.

코드 안에서도 마찬가지다. 하나의 클래스로 여러 객체를 만들 수 있고, 각 객체는 자기 상태를 따로 가진다.

이 점을 이해하고 나니 객체지향은 갑자기 멋있어 보이는 개념이 아니라, 현실을 꽤 정직하게 옮기는 방식처럼 보였다.

## `메서드 오버로딩`은 같은 이름 아래 다른 사용법을 허용하는 장치였다

5주차에서 또 인상적이었던 부분은 `메서드 오버로딩`이다. 처음엔 이름은 같고 매개변수만 다른 메서드를 왜 굳이 허용해야 하나 싶었는데, 교안의 `println()` 예시와 `Adder` 예시를 보니 이유가 꽤 분명했다.

같은 목적의 동작이라면 이름은 유지하되, 입력 방식이 다를 수 있다는 것이다.

### 같은 역할이라면 이름은 유지하고 입력만 달리할 수 있다

`add(int, int)`와 `add(float, float)`는 결국 둘 다 더하기다. 역할은 같은데 다루는 값의 형태가 다르다.

이런 경우 메서드 이름까지 전부 달라지면 오히려 읽기가 산만해질 수 있다. 그래서 자바는 같은 이름 아래 매개변수의 개수나 타입이 다른 메서드를 허용한다.

이걸 보고 나니 `오버로딩`은 문법적 편의가 아니라, 기능의 정체성을 유지하는 방식처럼 느껴졌다. 사용자는 같은 동작이라고 인식하는데 입력 방식이 다를 뿐이라면, 이름을 같게 두는 편이 훨씬 자연스럽다.

#### `println()`이 좋은 예시인 이유는 이미 익숙한 기능이기 때문이다

교안에서 `println()`의 여러 형태를 보여 주는 장면은 오버로딩을 이해하기에 꽤 적절했다. `boolean`, `char`, `int`, `String`, `Object`를 받아도 결국 사용자는 "출력한다"고 이해한다.

내부 처리는 달라도 바깥 개념은 같다. 그래서 메서드 이름이 유지되는 편이 훨씬 직관적이다.

이걸 보고 있으면 자바가 왜 문법을 그렇게 설계했는지도 조금 보인다. 기계가 이해하는 방식만이 아니라, 사람이 읽고 쓰는 방식도 같이 고려한 흔적처럼 느껴진다.

## `지역변수`는 어디까지 살아 있는가를 묻는 개념이었다

교안 후반부의 `지역변수` 설명도 꽤 중요했다. 메서드 안에서 선언한 변수, 매개변수, 블록 안에서 선언한 변수는 그 범위 안에서만 유효하다.

말로는 아주 단순한 규칙인데, 실제로는 코드가 커질수록 이 경계 감각이 정말 중요해진다.

### 값이 존재하는 범위를 모르면 읽는 사람도 쉽게 헷갈린다

`lv`처럼 메서드 내부에서만 쓰이는 값, `check`처럼 `if` 블록 안에서만 유효한 값은 그 범위를 넘어서면 더 이상 존재하지 않는다. 이 규칙은 제한처럼 보이지만, 오히려 코드를 덜 헷갈리게 만든다.

어디서 만들어졌고 어디서만 쓰이는지가 분명해지기 때문이다.

프로그램을 읽을 때 어려운 건 코드량보다도, 어떤 값이 지금 어디까지 살아 있는지 놓치는 순간이다. 그래서 지역변수는 사소한 문법처럼 보이지만, 코드의 경계를 읽는 연습이기도 하다.

### `인스턴스 변수`와 `지역변수`의 차이를 알면 클래스가 더 선명해진다

클래스 안에 선언된 변수는 객체가 살아 있는 동안 상태를 나타내는 값이고, 메서드 안의 지역변수는 특정 작업을 수행하는 동안 잠깐 쓰는 값이다.

이 차이를 이해하면 무엇을 클래스의 상태로 둘지, 무엇을 잠깐 계산용으로 둘지도 구분하기 쉬워진다.

이번 주차는 그래서 `클래스` 문법을 배운 시간이면서, 동시에 **값이 머무는 자리와 역할을 구분하는 감각**을 배우는 시간이기도 했다.

#### 잠깐 필요한 값과 오래 남아야 하는 값은 애초에 자리가 다르다

모든 값을 클래스 바깥쪽에 오래 들고 있을 필요는 없다. 어떤 값은 객체의 상태로 계속 남아 있어야 하지만, 어떤 값은 메서드 안에서 계산할 때 잠깐만 있으면 충분하다.

이 구분이 안 되면 클래스는 불필요하게 무거워지고, 반대로 지역변수로만 처리하면 객체가 기억해야 할 상태가 사라진다.

결국 `지역변수`를 배우는 일은 범위를 외우는 문제가 아니라, 값이 어디에 머물러야 자연스러운지 판단하는 연습에 더 가까웠다.

## 이번 5주차를 지나며 남은 건, `클래스`가 코드를 더 현실답게 만든다는 사실이다

이번 주차는 `클래스`, `인스턴스`, `메서드 오버로딩`, `지역변수`를 각각 배우는 시간처럼 보였지만, 실제로는 하나로 이어져 있었다.

무엇을 하나의 대상으로 볼지 정하고, 그 대상의 상태와 행동을 묶고, 실제 객체를 만들고, 같은 역할의 메서드를 더 자연스럽게 부르고, 필요한 범위 안에서만 값을 쓰는 흐름이 전부 하나의 설계 감각으로 이어졌기 때문이다.

그래서 이번 5주차는 자바가 갑자기 어려워진 시간이 아니라, 오히려 코드가 더 이해되는 방식으로 정리되기 시작한 시간처럼 남았다.

`클래스`는 문법이 아니라 설계의 최소 단위였고, 그걸 알고 나니 자바 코드가 조금 덜 낯설고 훨씬 더 구조적으로 보이기 시작했다.
