# [객체지향프로그래밍(JAVA)] 객체지향프로그래밍 학습 (6) - `배열`은 값이 많아지는 순간부터 문법이 아니라 구조가 된다

점수 다섯 개만 다뤄도 금방 이상해진다. `score1`, `score2`, `score3`처럼 이름을 늘려 쓰는 순간, 코드는 아직 돌아가도 읽는 사람 머릿속에서는 이미 정리가 무너지기 시작한다.

이번 6주차 `객체지향프로그래밍(JAVA)` 교안에서 `배열`을 다시 보면서 가장 크게 느낀 것도 그 지점이었다.

`배열`은 단순히 같은 타입 변수를 여러 개 저장하는 문법이 아니라, 값이 많아지는 순간 코드를 무너지지 않게 붙들어 주는 구조였다.

처음에는 `배열`을 초보 문법처럼 보기 쉽다. 그런데 막상 선언, 생성, 접근, `length`, 메서드 인자 전달, `2차원 배열`, `향상된 for문`, 그리고 `객체 배열`까지 이어서 보고 나면 생각이 조금 달라진다.

값을 많이 다룬다는 건 결국 순서와 범위를 같이 다룬다는 뜻이기 때문이다. 그래서 이번 주차는 값을 저장하는 방법을 배운 시간이면서, 동시에 **여러 데이터를 한 덩어리로 사고하는 방식**을 배우는 시간처럼 남았다.

## `배열`이 필요한 순간은 생각보다 빨리 온다

교안 초반에서 `변수`와 `배열`의 차이를 비교하는 부분은 기본 설명처럼 보이지만 꽤 오래 남는다. 변수는 하나의 데이터를 저장하고, 배열은 같은 타입의 여러 데이터를 저장한다.

문장으로는 간단한데, 실제로는 이 차이가 코드 구조 전체를 바꾼다. 하나씩 이름 붙여 관리하던 값을 같은 성격의 데이터 묶음으로 보기 시작하면 이후의 처리 방식도 함께 달라지기 때문이다.

### 변수 이름만 늘리는 방식이 왜 금방 버거워질까

예를 들어 국어 점수 열 개를 저장한다고 해 보자. `korScore1`, `korScore2`, `korScore3`처럼 이름을 붙여 가는 순간, 저장은 되더라도 반복 처리나 합계 계산, 평균 계산은 금방 불편해진다.

값의 개수가 늘수록 변수의 이름을 기억하는 일 자체가 일이 된다. 코드는 데이터를 관리하는 도구여야 하는데, 오히려 사람이 이름을 관리하느라 힘을 쓰게 되는 셈이다.

이 지점에서 `배열`은 자연스럽게 등장한다. 같은 종류의 값들이라면 하나의 이름 아래 순서만 붙여 관리하는 편이 훨씬 낫기 때문이다.

### 같은 타입의 값들을 한 묶음으로 본다는 발상이 생긴다

`배열`의 핵심은 단지 공간을 많이 만든다는 데 있지 않다. 같은 타입의 값을 하나의 구조로 묶어 보고, 그 안에서 몇 번째 값인지를 기준으로 다룬다는 데 있다.

이 발상이 생기면 데이터는 흩어진 변수들의 집합이 아니라, 일정한 규칙을 가진 집합처럼 보이기 시작한다. 그래서 `배열`은 저장 방식인 동시에 사고 방식의 변화이기도 했다.

## `배열 선언`과 `생성`은 저장공간을 한 번에 확보하는 감각이었다

교안에서 `배열`을 설명할 때 `배열 변수 선언`과 `배열 생성`을 나누어 보여 주는 이유도 분명했다. `int[] numbers;`와 `numbers = new int[5];`는 한 줄처럼 이어 보이지만, 실제로는 의미가 다르다.

하나는 배열을 가리킬 이름을 만드는 일이고, 다른 하나는 실제로 배열 인스턴스를 생성하는 일이다. 이 차이를 이해해야 배열이 값 다섯 개짜리 특별한 변수 묶음이 아니라, 메모리 위에 생성되는 하나의 객체처럼 보인다.

### `int[] numbers`와 `new int[5]`는 역할이 다르다

`int[] numbers`는 아직 아무 값도 저장하지 않은 이름이다. 반면 `new int[5]`는 정수 다섯 개를 저장할 수 있는 실제 배열 공간을 만든다.

이 둘이 합쳐져야 비로소 배열이 동작한다. 그래서 `배열`을 볼 때는 선언과 생성을 같은 문법 덩어리로만 외우기보다, 이름과 실체가 만나는 장면으로 이해하는 편이 더 선명했다.

객체지향을 먼저 배운 흐름과도 잘 연결된다. `클래스`에서 `인스턴스`를 만들던 방식처럼, 배열도 결국 `new`를 통해 실제 공간을 만든다.

### 인덱스를 쓴다는 건 위치로 접근하겠다는 약속이다

배열을 만들고 나면 각 요소는 `0`부터 시작하는 `index`로 접근한다. 처음엔 이 `0`부터 시작한다는 규칙이 약간 낯설지만, 오히려 이 규칙이 있기 때문에 위치가 분명해진다.

`numbers[0]`, `numbers[1]`, `numbers[2]`처럼 접근하는 방식은 각 값에 별도의 이름을 주는 대신, 전체 구조 안에서의 순서로 값을 식별한다. 배열은 개별 이름보다 위치를 더 믿는 구조인 셈이다.

#### `length`를 같이 보는 순간 범위 감각이 생긴다

교안에서 `length`를 강조하는 부분도 꽤 중요했다. 배열은 만들어지는 순간 길이가 정해지고, 그 길이만큼만 유효한 인덱스를 가진다.

즉 `numbers.length`를 안다는 건 배열이 몇 칸짜리인지 안다는 뜻이고, 동시에 어디까지 접근할 수 있는지도 안다는 뜻이다. 이 감각이 있어야 범위를 벗어나는 실수를 덜 하게 된다.

배열을 다루는 사람에게 중요한 건 단순히 값을 넣는 능력이 아니라, **유효한 범위를 끝까지 의식하는 습관**이라는 생각도 들었다.

## 값을 꺼내고 채우는 과정에서 `for`문이 자연스럽게 붙는다

배열이 흥미로운 이유는 저장보다 처리에서 더 드러난다. 값을 하나하나 읽고 쓰는 순간, `for`문이 거의 자동처럼 따라붙기 때문이다.

배열은 순서가 있는 구조이고, `for`문은 그 순서를 차례로 따라가는 제어문이다. 그래서 둘은 같이 놓였을 때 가장 자연스럽다.

### 순차적 접근은 배열이 가장 잘하는 일이다

교안의 예제처럼 배열 요소를 처음부터 끝까지 차례대로 출력하거나 합계를 구하는 작업은 배열의 장점을 가장 잘 보여 준다. 인덱스를 하나씩 증가시키면서 같은 패턴을 반복하면 되기 때문이다.

이런 순차 접근은 배열이 강한 이유이기도 하다. 메모리 구조가 연속적이어서 읽는 흐름이 단순하고, 처리 과정도 예측 가능하다.

그래서 배열은 값을 많이 저장하는 구조인 동시에, 같은 규칙으로 많이 처리하는 구조이기도 하다.

### 선언과 동시에 초기화하면 읽는 속도가 달라진다

교안에서 `{100, 90, 80, 70, 60}`처럼 선언과 동시에 값을 넣는 예제를 보여 주는 부분도 좋았다. 값의 목록이 이미 정해져 있을 때는 이 방식이 훨씬 읽기 쉽다.

한 줄만 봐도 배열 길이와 들어가는 값의 흐름이 같이 보이기 때문이다. 코드는 실행만 되면 되는 게 아니라 읽히는 편이 더 좋다는 걸 이런 장면에서 다시 느끼게 된다.

## `배열을 메서드에 전달`한다는 건 데이터 묶음을 통째로 건네는 일이었다

6주차에서 특히 인상 깊었던 부분은 `배열`을 `메서드`의 인자로 넘기는 장면이다. 이전까지는 메서드에 값 하나, 두 개 정도를 전달하는 데 익숙했다면, 이번에는 데이터 묶음 전체를 넘긴다.

이 순간 배열은 저장공간을 넘어서 처리의 단위가 된다. 메서드는 더 이상 개별 점수 하나를 받아 계산하는 것이 아니라, 점수 목록 전체를 받아 의미 있는 결과를 만든다.

### 합계와 평균 예제가 기본인데도 오래 남는 이유

합계와 평균 예제는 아주 전형적이다. 그런데 전형적인 예제인 만큼 본질을 잘 보여 준다.

배열을 인자로 넘기고, 메서드 안에서 `for`문으로 모든 요소를 순회해 합계를 구하고, 길이로 나누어 평균을 계산하는 흐름은 `배열`이 왜 필요한지를 정직하게 설명한다. 값이 많아질수록 묶어서 넘기는 편이 훨씬 자연스럽기 때문이다.

### 배열 하나를 넘기면 메서드의 책임이 더 분명해진다

점수 목록을 받아 평균을 구하는 메서드, 회원 목록을 받아 이름을 출력하는 메서드처럼 생각하기 시작하면, 로직도 훨씬 구조적으로 보인다.

즉 배열을 메서드에 전달하는 일은 문법 하나를 더 배우는 게 아니라, **함수가 데이터를 어떤 크기로 받아야 자연스러운가**를 배우는 일이기도 했다.

## `2차원 배열`은 값이 아니라 표를 다루는 감각에 가까웠다

교안 후반부에서 `2차원 배열`로 넘어가는 장면도 좋았다. `1차원 배열`이 한 줄에 놓인 값들이라면, `2차원 배열`은 행과 열을 가진 표에 가깝다.

이 순간부터 배열은 숫자 목록이 아니라 장면처럼 보이기 시작한다. 몇 행 몇 열인지, 어느 행의 어느 칸인지가 같이 중요해지기 때문이다.

### 행과 열이 생기면 데이터가 장면처럼 보인다

`arr[0][1]`, `arr[1][2]`처럼 접근하는 방식은 처음엔 괄호가 많아져서 복잡해 보인다. 그런데 한 번 감이 잡히면 오히려 구조가 더 명확해진다.

첫 번째 인덱스는 행, 두 번째 인덱스는 열을 뜻한다는 약속만 이해하면 된다. 그러면 `2차원 배열`은 단순한 중첩이 아니라 표 형태 데이터를 다루는 기본 틀로 읽힌다.

### 점수표, 좌석표, 시간표 같은 예시가 잘 들어맞는다

반별 점수표, 극장 좌석표, 주간 시간표처럼 행과 열로 정리되는 데이터는 생각보다 많다. 이런 데이터를 변수나 `1차원 배열`만으로 표현하려 하면 금방 꼬인다.

반면 `2차원 배열`은 구조가 이미 표 형태를 닮아 있어서 훨씬 자연스럽다. 문법 설명이 구조 이해로 이어졌다는 점이 이번 단원의 가장 좋은 점이었다.

## `향상된 for문`과 `객체 배열`까지 가면 배열의 쓰임이 확 넓어진다

6주차의 마지막 흐름은 꽤 매끄러웠다. 배열 요소를 `for`문으로 순회하는 것에 익숙해진 뒤, `향상된 for문`과 `객체 배열`로 넘어가니 배열이 더 이상 숫자 전용 구조가 아니라는 점이 자연스럽게 보였다.

### `for-each`는 읽기 좋지만 위치 제어는 약하다

`for (int score : scores)`처럼 쓰는 `향상된 for문`은 확실히 읽기 편하다. 인덱스를 직접 다루지 않아도 전체 요소를 순회할 수 있기 때문이다.

다만 위치 정보가 필요한 경우에는 일반 `for`문이 더 낫다. 몇 번째 요소인지 알아야 하거나 특정 인덱스를 수정해야 하면 결국 인덱스 기반 반복이 필요하다.

### `Member[]` 같은 배열을 보면 객체지향과 배열이 연결된다

교안 마지막의 `객체를 다루는 배열`은 꽤 상징적이었다. `int[]`처럼 기본형만 저장하는 것이 아니라 `Member[]`처럼 객체를 저장하는 순간, 배열과 객체지향이 한 장면에서 만난다.

이 장면을 보고 나니 배열은 기본형 데이터 묶음에만 쓰는 문법이 아니라, **여러 객체를 한꺼번에 다루기 위한 가장 기초적인 컨테이너**처럼 느껴졌다.

## 이번 6주차에서 남은 건, `배열`은 많아진 값을 정리하는 가장 기본적인 구조라는 사실이었다

이번 주차는 `배열 선언`, `배열 생성`, `요소 접근`, `length`, `메서드 인자 전달`, `2차원 배열`, `향상된 for문`, `객체 배열`까지 이어지면서 생각보다 많은 걸 한 번에 보여 줬다.

겉으로 보면 전부 배열 문법 이야기 같지만, 실제로는 하나의 흐름이었다. 값이 많아질수록 묶어서 보고, 순서대로 처리하고, 필요하면 표처럼 확장하고, 나중에는 객체까지 담아 다루는 흐름 말이다.

그래서 이번 6주차는 자바에서 배열을 배운 시간이면서도, 동시에 데이터를 **몇 개의 값이 아니라 하나의 구조로 이해하는 출발점**을 배운 시간처럼 남았다.

값이 많아지는 순간부터 `배열`은 선택이 아니라 거의 필수적인 정리 방식이었다.
