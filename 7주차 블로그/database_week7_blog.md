# [데이터베이스] 데이터베이스 학습 (7) - `관계대수`와 `관계해석`으로 정리하는 관계 데이터 연산

데이터베이스를 배울 때 자꾸 `SQL` 문장부터 떠올리게 된다. 무엇을 조회할지보다 `SELECT`를 어떻게 써야 할지 먼저 생각나는 식이다. 그런데 이번 7주차 `데이터베이스` 교안을 보고 나니, 그 전에 한 번 더 거쳐야 할 층이 있다는 게 보였다.

바로 `관계 데이터 연산`이다. 어떤 데이터를 골라낼지, 어떤 속성만 남길지, 두 릴레이션을 어떻게 묶을지, 조건을 절차적으로 말할지 선언적으로 말할지를 먼저 정리하는 층 말이다.

이번 주차는 `관계대수`와 `관계해석`을 중심으로 진행된다. `합집합`, `교집합`, `차집합`, `카티전 프로덕트` 같은 일반집합 연산자부터 `선택`, `프로젝트`, `조인`, `디비전` 같은 순수관계 연산자까지 나온다. 그리고 그 뒤에 절차적 표현인 `관계대수`와 비절차적 표현인 `관계해석`의 차이가 이어진다.

전체 흐름을 보고 나니 이번 주차는 쿼리 문법을 배우는 시간이 아니라, 원하는 데이터를 어떤 논리로 설명할지 배우는 시간에 더 가까웠다.

## `관계 데이터 연산`의 의미

교안 첫 부분은 관계 데이터 연산이 관계형 데이터베이스에서 데이터를 관리하기 위해 사용되는 연산이라고 설명한다. 아주 교과서적인 문장인데, 막상 예시를 따라가다 보면 생각보다 실용적으로 느껴진다.

### 질문을 연산으로 바꾸는 과정

예를 들어 "점수가 90 이상인 학생을 찾고 싶다", "과목명과 점수만 보고 싶다", "구매 정보와 상품 정보를 연결해서 가격이 40 미만인 상품만 보고 싶다" 같은 요구는 전부 데이터 연산의 문제다.

이걸 그냥 말로만 하면 막연하지만, 어떤 릴레이션에서 무엇을 기준으로 고르고, 어떤 속성만 남기고, 어떤 릴레이션과 결합할지를 연산으로 표현하는 순간 요구가 훨씬 분명해진다.

### `SQL` 이전의 연산 의도

이번 주차를 보며 더 크게 느낀 건, 쿼리를 잘 쓰는 일은 문법 암기보다 의도 정리가 먼저라는 점이었다. 무엇을 추려 낼지와 어떤 순서로 처리할지를 모르는데 문장만 안다고 해서 좋은 질의가 나오기는 어렵다.

`관계대수`와 `관계해석`은 바로 그 의도 정리의 바닥을 만들어 주는 개념처럼 느껴졌다.

## `관계대수` 개념과 절차성

교안은 `관계대수`를 데이터베이스에서 데이터를 처리하기 위한 절차적 언어라고 설명한다. 사용자가 원하는 결과를 얻기 위해 데이터의 처리 과정을 순서대로 기술하는 방식이라는 뜻이다.

### 처리 순서와 연산 흐름

`σ가격<=40(상품)`처럼 조건에 맞는 튜플을 먼저 고를 수도 있고, `π고객번호, 상품코드(...)`처럼 필요한 속성만 남길 수도 있다. 그리고 필요하면 `구매 ∞ 상품`처럼 두 릴레이션을 조인한 뒤 다시 조건을 걸 수도 있다.

이 흐름을 보면 관계대수는 "최종 결과가 뭐냐"만 말하는 게 아니라, 그 결과에 도달하기까지의 연산 순서를 함께 드러낸다.

### 절차적 표현의 의미

어떤 연산을 먼저 하고 어떤 연산을 뒤에 둘지 드러나기 때문에, 관계대수는 문제 풀이 과정을 보여 주는 느낌이 강하다. 그래서 처음에는 어렵게 느껴져도, 한 번 익숙해지면 질의 의도를 명확히 설명하는 데 꽤 유용하다.

교안에서 수식 형태로 여러 예시를 보여 주는 이유도 바로 여기에 있는 것 같았다. 단순히 기호를 배우는 게 아니라 데이터 요구를 논리적 절차로 바꾸는 연습이기 때문이다.

#### 관계대수 식 구조

```text
π고객번호, 상품코드 (
    σ가격 <= 40 (
        구매 ∞ 상품
    )
)
```

이 식은 먼저 `구매`와 `상품`을 `조인`하고, 그 결과에서 `가격 <= 40`인 튜플만 `선택`한 뒤, 마지막에 `고객번호`와 `상품코드`만 `프로젝트`한다는 뜻이다. 교안에서 기호가 낯설게 보였다면 이렇게 줄을 나눠 읽는 것만으로도 훨씬 덜 복잡해진다.

#### 관계대수와 `SQL` 대응

```sql
SELECT p.고객번호, p.상품코드
FROM 구매 p
JOIN 상품 s
    ON p.상품코드 = s.상품코드
WHERE s.가격 <= 40;
```

이렇게 나란히 놓고 보면 `관계대수`가 왜 중요한지도 더 잘 보인다. `SQL` 문장을 바로 외우는 것보다, 먼저 어떤 연산을 하고 싶은지 구조를 이해하면 쿼리도 훨씬 덜 막힌다.

## `일반집합 연산자` 핵심

7주차 초반에는 `합집합`, `교집합`, `차집합`, `카티전 프로덕트` 같은 일반집합 연산자가 먼저 정리된다.

### `합집합`, `교집합`, `차집합` 조건

교안에서 계속 강조되는 건 이 세 연산을 쓰려면 두 릴레이션이 서로 합병 가능해야 한다는 점이다. `차수`가 같아야 하고, 대응되는 속성의 `도메인`도 같아야 한다.

이 조건이 없으면 같은 위치의 값을 같은 종류로 볼 수 없기 때문에 연산 자체가 어색해진다. 결국 집합 연산은 보기보다 엄격한 전제를 깔고 있다.

### `카티전 프로덕트`와 `조인`의 바닥

`R × S`는 두 릴레이션의 모든 튜플 조합을 만들어 낸다. 겉으로 보면 과한 연산처럼 느껴질 수 있지만, 교안을 따라가다 보면 `조인`을 이해하는 데 중요한 바닥이라는 걸 알게 된다.

모든 조합을 만든 뒤 조건으로 걸러 내는 관점이 있어야 `세타 조인`이나 `동등 조인`이 어떻게 동작하는지도 더 잘 보인다.

## `선택`과 `프로젝트` 차이

순수관계 연산자 중에서 가장 먼저 익숙해지는 건 아마 `선택(Select, σ)`과 `프로젝트(Project, π)`일 것이다.

### `선택(σ)`과 행 필터링

교안은 `선택`을 릴레이션에서 조건에 만족하는 튜플을 검색하는 연산으로 설명한다. 학생 테이블에서 점수가 90 이상인 학생만 찾거나, 고객 테이블에서 `gold` 등급이면서 적립금이 2000 이상인 튜플만 찾는 예시가 나온다.

여기서 중요한 건 `선택`이 속성을 줄이는 게 아니라 튜플을 줄인다는 점이다. 즉 열은 그대로 두고, 조건을 만족하는 행만 남긴다.

#### `선택`과 `WHERE` 대응

```sql
SELECT *
FROM 학생
WHERE 점수 >= 90;
```

이 쿼리는 열은 그대로 둔 채, 조건을 만족하는 행만 남긴다. 그래서 `선택`을 이해할 때는 "행을 줄이는 연산"이라는 말을 그냥 외우기보다, `WHERE`가 붙은 조회를 떠올리면 훨씬 덜 헷갈린다.

### `프로젝트(π)`와 열 추출

반대로 `프로젝트`는 릴레이션에서 주어진 속성들의 값으로만 구성된 열을 선택한다. 학생 릴레이션에서 `과목, 점수`만 보거나, 성적 릴레이션에서 `Name`과 `Avg`만 추려내는 식이다.

처음엔 `선택`과 헷갈릴 수 있지만, 하나는 행을 걸러 내고 하나는 열을 줄인다는 점만 분명히 잡아도 훨씬 안정된다.

```sql
SELECT 과목, 점수
FROM 학생;
```

이 경우에는 반대로 행 수는 그대로 두고, 필요한 열만 남긴다. `선택`과 `프로젝트`를 이렇게 각각 SQL로 대응해 보면, `σ`와 `π`를 시험에서 구분할 때도 훨씬 덜 헷갈린다.

#### `σ`와 `π` 구분 포인트

실제로 질의를 만들 때는 둘이 함께 쓰인다. 조건으로 필요한 튜플을 좁힌 뒤, 마지막에 꼭 필요한 속성만 남기는 흐름이 자주 나온다.

이번 주차를 보며 느낀 건 이 둘이 단순한 기본 연산이 아니라, 데이터 질의를 정리하는 가장 핵심적인 축이라는 점이었다.

## `조인` 핵심 구조

후반부에서 가장 분량이 큰 건 역시 `조인(Join, ∞)`이다. 공동 속성을 이용해 두 개 이상의 릴레이션을 연결하여 새로운 릴레이션을 만드는 연산으로 설명된다.

### `조인`의 의미와 문맥 연결

직원 릴레이션과 부서 릴레이션, 구매 릴레이션과 상품 릴레이션처럼 실제 데이터베이스는 보통 정보가 나뉘어 저장된다. 그런데 사용자가 원하는 결과는 자주 그 분리된 정보의 결합 형태다.

그래서 `조인`은 단순한 결합 연산이 아니라, 데이터베이스가 왜 여러 테이블로 나뉘어 있으면서도 하나의 시스템처럼 보일 수 있는지 설명해 주는 핵심 연산처럼 느껴졌다.

### `내부 조인`과 `외부 조인` 차이

교안은 `내부 조인`, `왼쪽 외부 조인`, `오른쪽 외부 조인`, `전체 외부 조인`을 함께 보여 준다. 둘 모두 조건을 기준으로 연결하지만, 조건을 만족하지 않는 행을 결과에서 버릴지, `NULL`을 채워서라도 남길지가 달라진다.

이 차이는 조회 결과를 해석하는 데 꽤 중요하다. 같은 테이블을 묶어도 어떤 조인을 택하느냐에 따라 "없는 데이터"가 보이는 방식이 달라지기 때문이다.

### `세타 조인`, `동등 조인`, `자연 조인` 차이

`세타 조인`은 `<, >, =` 같은 비교 연산자를 넓게 허용하고, `동등 조인`은 속성 값이 같은 경우를 연결하고, `자연 조인`은 공통 속성을 기준으로 자연스럽게 중복을 줄여 묶는다.

교안 예시를 보고 있으면 조인은 한 종류가 아니라, 조건을 어떤 방식으로 거느냐에 따라 성격이 달라지는 큰 묶음처럼 느껴진다.

#### `JOIN` 문장 비교 예시

```sql
SELECT e.사원명, d.부서명
FROM 사원 e
INNER JOIN 부서 d
    ON e.부서번호 = d.부서번호;
```

```sql
SELECT e.사원명, d.부서명
FROM 사원 e
LEFT OUTER JOIN 부서 d
    ON e.부서번호 = d.부서번호;
```

첫 번째는 연결되는 데이터만 남기는 `내부 조인`이고, 두 번째는 왼쪽 릴레이션 기준으로 연결되지 않는 행도 살려 두는 `외부 조인`이다. 같은 테이블을 대상으로 해도 결과 해석이 달라지는 이유가 여기서 분명해진다.

## `디비전(÷)` 연산 핵심

이번 주차에서 가장 낯설면서도 흥미로웠던 건 `디비전(Division, ÷)`이었다.

### 모든 조건 만족 검색

교안 예시처럼 `고객 ÷ 클래스` 형태를 보면, B 릴레이션의 모든 조건을 만족하는 튜플을 A 릴레이션에서 구하는 연산이라는 설명이 붙는다.

이건 단순히 하나의 조건을 만족하는 데이터를 찾는 문제보다 더 강하다. 특정 집합 전체를 충족하는 대상을 찾는 문제이기 때문이다.

### `디비전`이 필요한 질의 구조

일상적인 조회에서는 자주 안 보일 수 있어도, 조건의 "전체 충족"을 표현해야 하는 순간엔 꽤 강력하다. 이번 주차가 좋았던 건 이런 덜 익숙한 연산도 관계형 질의의 표현력 안에 포함된다는 걸 보여 준다는 점이었다.

#### `디비전`과 `NOT EXISTS` 대응

```sql
SELECT s.학생번호
FROM 수강 s
WHERE NOT EXISTS (
    SELECT 1
    FROM 필수과목 r
    WHERE NOT EXISTS (
        SELECT 1
        FROM 수강 s2
        WHERE s2.학생번호 = s.학생번호
          AND s2.과목번호 = r.과목번호
    )
);
```

표현은 길지만 뜻은 분명하다. `필수과목`에 있는 모든 과목을 빠짐없이 수강한 학생만 남기겠다는 의미다. 그래서 `디비전`은 낯선 기호처럼 보여도, 실제로는 "모든 조건을 만족하는 대상을 찾는 연산"이라고 이해하면 훨씬 덜 어렵다.

## `관계해석` 개념과 선언 방식

`관계해석`은 관계대수와 함께 나오는 또 하나의 큰 축이다. 교안은 데이터를 처리하기 위한 비절차적인 언어라고 정리한다.

### `관계대수`와 `관계해석` 차이

관계대수가 연산 순서를 드러낸다면, 관계해석은 어떤 조건을 만족하는 데이터가 필요한지를 더 중심에 둔다. 사용자가 원하는 결과의 조건을 기술하는 방식인 셈이다.

이 차이를 보고 나니 두 개념이 서로 경쟁하는 게 아니라 서로 다른 관점을 제공한다는 느낌이 들었다. 하나는 절차를, 다른 하나는 조건을 강조한다.

### 절차적 언어와 비절차적 언어 비교

`SQL`은 현실에서는 절차와 선언이 섞여 보일 때도 많지만, 큰 흐름에서는 원하는 결과를 선언하는 언어라는 점에서 관계해석 쪽 감각과 더 맞닿아 있다. 반면 관계대수는 내부 연산 논리를 이해하는 데 더 직관적이다.

그래서 이번 주차는 두 이론을 분리해서 외우는 것보다, 하나는 처리 과정의 사고 훈련이고 다른 하나는 조건 표현의 사고 훈련이라고 이해하는 편이 더 잘 남았다.

## 7주차 핵심 정리

이번 주차는 `관계대수`, `관계해석`, `합집합`, `교집합`, `차집합`, `카티전 프로덕트`, `선택`, `프로젝트`, `조인`, `디비전`까지 이어지면서 관계형 데이터베이스에서 데이터를 꺼내는 사고방식을 훨씬 또렷하게 만들어 줬다.

무엇을 보고 싶은지 말할 때도, 그걸 절차적으로 설명할지 선언적으로 설명할지에 따라 표현 방식이 달라진다. 그래서 이번 7주차는 SQL을 배우기 전 단계 같으면서도, 사실은 SQL을 더 잘 이해하기 위한 핵심 바닥처럼 느껴졌다.

## 중간고사 정리 포인트

6주차까지 `릴레이션`, `속성`, `도메인`, `키`, `무결성`을 배웠다면 7주차는 그 구조 위에서 실제로 어떤 연산을 할 수 있는지를 보여 주는 단계다. 구조를 알기만 해서는 아직 데이터베이스가 덜 살아 있는데, `선택`, `프로젝트`, `조인`이 붙는 순간 비로소 데이터를 쓰는 감각이 생긴다.

중간고사 준비를 할 때도 `관계대수` 기호만 외우기보다, `행을 줄이는 연산`, `열을 줄이는 연산`, `릴레이션을 묶는 연산`, `집합 전체를 만족시키는 연산`처럼 역할별로 묶어 정리하는 편이 더 오래 남을 것 같았다. 특히 `합병 가능 조건`, `σ`, `π`, `∞`, `÷`, 그리고 `절차적/비절차적` 차이는 꼭 짚어 두는 게 좋겠다 싶었다.
