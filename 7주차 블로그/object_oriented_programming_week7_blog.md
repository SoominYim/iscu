# [객체지향프로그래밍(JAVA)] 객체지향프로그래밍 학습 (7) - `상속`, `오버라이딩`, `다형성` 핵심 정리

비슷한 클래스가 두세 개쯤 생기기 시작하면, 처음에는 그냥 조금만 더 쓰면 될 것 같다가도 어느 순간 코드가 갑자기 무거워진다. `Phone`에도 전화번호가 있고 `SmartPhone`에도 전화번호가 있고, 둘 다 통화 기능이 있는데 따로따로 또 적고 있다면 더 그렇다.

이번 7주차 `객체지향프로그래밍(JAVA)` 교안은 바로 그 지점에서 `상속`을 꺼내 든다. 새 클래스를 만드는 법을 하나 더 배우는 느낌이라기보다, 이미 있는 클래스를 어떻게 이어받고 확장할지를 배우는 시간에 더 가까웠다.

교안 흐름도 꽤 선명했다. `클래스의 상속` 개념부터 시작해서 `IS-A`와 `HAS-A`, `super`를 이용한 상위 멤버 호출, 생성자 호출, `오버라이딩`, `업캐스팅`과 `다운캐스팅`, `instanceof`, 그리고 마지막에는 `다형성`을 이용한 애플리케이션 관리 예시까지 자연스럽게 이어졌다.

이번 주차를 보고 나니 상속은 단순히 코드 재사용을 위한 문법이 아니라, 클래스 사이의 관계를 더 정확하게 표현하기 위한 도구라는 쪽이 더 크게 남았다.

## `상속`과 관계 구조

교안 초반은 `Parent`와 `Child`, `Phone`과 `SmartPhone`처럼 아주 전형적인 예시로 시작한다. 이미 정의한 클래스의 멤버와 메소드를 물려받아 새로운 클래스를 정의하는 구조 말이다.

처음엔 이걸 그냥 중복 제거 정도로만 받아들이기 쉽다. 실제로도 상속은 중복을 줄이는 데 도움이 된다. 하지만 이번 주차를 따라가다 보면 더 중요한 건 "둘이 어떤 관계인가"를 코드에 드러내는 데 있다는 걸 알게 된다.

### `extends`와 상속 구조

`class Child extends Parent`처럼 쓰는 문장은 짧지만 의미는 꽤 크다. 자식 클래스는 부모 클래스의 변수와 메소드를 물려받고, 필요하면 자기만의 멤버를 추가할 수도 있다.

교안의 `Phone`과 `SmartPhone` 예시도 딱 그 흐름이다. `Phone`은 `phoneNumber`와 `call()`을 가지고 있고, `SmartPhone`은 그걸 그대로 이어받은 뒤 `model`과 `game()`을 추가한다.

이 구조를 보면 상속은 "부모 코드를 복사해서 갖다 쓰는 기술"이 아니다. 이미 정의된 성질을 바탕으로 새로운 클래스를 자연스럽게 확장하는 기술에 더 가깝다.

#### `상속` 코드 구조

```JAVA
class Phone {
    String phoneNumber;

    Phone(String phoneNumber) {
        this.phoneNumber = phoneNumber;
    }

    void call() {
        System.out.println(phoneNumber + "로 통화합니다.");
    }
}

class SmartPhone extends Phone {
    String model;

    SmartPhone(String phoneNumber, String model) {
        super(phoneNumber);
        this.model = model;
    }

    void game() {
        System.out.println(model + "에서 게임을 실행합니다.");
    }
}
```

이 예시를 코드로 직접 보면 왜 `SmartPhone`이 `Phone`의 한 종류인지 훨씬 또렷해진다. 전화번호와 통화 기능은 부모에서 가져오고, 자식은 자기 역할인 `model`, `game()`만 덧붙인다. 같은 기능을 다시 쓰지 않아도 된다는 점도 보이지만, 그보다 "어디까지가 공통이고 어디부터가 확장인지"가 코드에서 자연스럽게 분리된다는 점이 더 중요했다.

### 상속의 장점과 설명 구조

`SmartPhone`이 전화기이기도 하다는 사실이 코드 안에 그대로 남는다는 점이 중요했다. 만약 전화번호와 통화 메소드를 자식 클래스에 전부 다시 적었다면 기능은 만들 수 있어도 관계는 흐려진다.

상속을 쓰는 순간 `SmartPhone`은 "전화 기능을 가진 새로운 객체"가 아니라 "전화기라는 성질을 이어받은 확장 클래스"가 된다. 코드 양보다 의미 전달이 더 좋아지는 것이다.

## `IS-A`와 `HAS-A` 구분

교안에서 특히 좋았던 부분은 `IS-A` 관계와 `HAS-A` 관계를 분리해서 설명하는 장면이었다. 상속을 언제 써야 하는지가 여기서 훨씬 선명해진다.

### 자연스러운 상속 관계와 어색한 관계

`SmartPhone IS-A Phone`은 자연스럽다. 스마트폰은 전화기의 한 종류라고 말해도 전혀 어색하지 않기 때문이다. 그래서 상속으로 풀어도 설계가 납득된다.

반면 교안의 `Point`와 `Line` 예시는 다르다. 선분은 점을 포함할 수는 있어도 점의 한 종류는 아니다. 이 관계는 `IS-A`보다 `HAS-A`에 가깝다.

그래서 `Line` 안에 `Point point1`, `Point point2`를 두는 방식이 나온다. 상속으로 풀지 않고 포함 관계로 표현한 것이다. 이 구분이 생각보다 중요했다.

### 잘못된 관계 설정의 문제

상속은 강한 관계다. 부모 클래스의 성질을 물려받고, 타입 체계에도 영향을 준다. 그런데 단순히 "같이 쓰이니까"라는 이유로 상속을 써 버리면 나중에 메소드나 필드 의미가 틀어지기 쉽다.

교안을 보며 느낀 건, 상속은 편한 재사용 수단이기 전에 관계 판단부터 필요한 설계 선택이라는 점이었다. 무엇을 닮았는지가 아니라, 무엇의 한 종류인지를 먼저 물어봐야 한다.

## `super`와 `this` 사용 구조

7주차 중반부에서는 상속 관계 안에서 같은 이름의 변수와 메소드를 어떻게 구분하는지가 나온다. 이 부분은 문법처럼 보이지만, 실제로는 상속 구조를 이해하는 데 꼭 필요한 감각이었다.

### 동일 이름 멤버와 참조 위치 차이

교안 예시에서는 부모 클래스의 `num = 10`, 자식 클래스의 `num = 100`이 같이 등장한다. 그리고 `showData()` 안에서 `super.num`과 `this.num`을 각각 출력한다.

이 예시가 좋았던 건, 상속이 된다고 해서 자식 클래스 안에 부모의 멤버가 흐릿하게 섞이는 게 아니라는 점을 보여 주기 때문이다. 상위 클래스의 멤버를 명확히 부를 때는 `super`, 현재 인스턴스의 멤버를 가리킬 때는 `this`를 쓴다.

### 부모 메소드 확장 방식

`super.call()`처럼 상위 클래스의 메소드를 먼저 호출한 뒤 자식 클래스 동작을 덧붙이는 패턴도 나온다. 이 부분이 상속을 단순 재정의보다 더 입체적으로 보게 만들었다.

예를 들어 `SmartPhoneImpl`이 통화 메소드를 `오버라이딩`하면서도, 먼저 `super.call()`을 실행하고 그 뒤에 "이어팟을 이용해서 통화합니다" 같은 자식만의 동작을 붙일 수 있다. 부모 기능을 완전히 끊지 않고 이어받아 확장하는 방식이다.

#### `super`와 `오버라이딩` 코드 흐름

```JAVA
class SmartPhoneImpl extends Phone {
    SmartPhoneImpl(String phoneNumber) {
        super(phoneNumber);
    }

    @Override
    void call() {
        super.call();
        System.out.println("이어팟을 이용해서 통화합니다.");
    }
}
```

이 코드는 왜 `오버라이딩`이 단순 덮어쓰기와 다르다고 하는지 잘 보여 준다. 부모가 하던 일을 완전히 지워 버리는 게 아니라, 부모 기능을 먼저 실행한 다음 자식만의 동작을 덧붙일 수 있다. 그래서 `super`는 그냥 상위 멤버를 부르는 문법이라기보다, 상속 구조 안에서 "공통 동작을 어디까지 유지할 것인가"를 드러내는 장치처럼 느껴졌다.

#### `super` 키워드의 의미

코드를 읽을 때 `super`가 보이면 지금 로직이 부모 쪽 성질을 일부러 끌어오고 있다는 뜻이다. 이게 보이기 시작하면 상속 구조 안에서 어디까지가 공통 기능이고 어디부터가 자식의 추가 기능인지 훨씬 쉽게 읽힌다.

## `생성자 호출`과 초기화 책임

이번 주차에서 상속이 더 깊어지는 지점은 생성자였다. 멤버를 물려받는 것만이 아니라, 상위 클래스가 가진 값을 어떻게 초기화할지까지 연결되기 때문이다.

### 부모 필드 초기화 방식

`Phone`이 `phoneNumber`를 갖고 있다면, `SmartPhone` 생성 시점에 그 값도 함께 제대로 세팅돼야 한다. 교안은 `super(phoneNumber)`를 통해 부모 생성자를 호출하는 방식을 보여 준다.

이 흐름을 보면서 상속은 "기능을 이어받는다"는 말로는 부족하다는 생각이 들었다. 객체가 생성될 때 필요한 초기화 순서까지 포함해 설계해야 하기 때문이다.

### `super()` 호출의 역할

부모가 관리해야 하는 필드는 부모 생성자가 책임지는 편이 자연스럽다. 자식 클래스가 그걸 억지로 끌어다 직접 세팅하는 것보다 구조도 깔끔하고 의미도 분명하다.

그래서 생성자 호출 부분은 자잘한 문법 설명이 아니라, 클래스마다 맡아야 할 초기화 책임이 다르다는 걸 보여 주는 장면으로 읽혔다.

## `오버라이딩`과 `다형성` 구조

후반부부터는 상속이 왜 실제 코드에서 강한지 보여 주는 내용이 본격적으로 나온다. `오버라이딩`과 `다형성` 때문이다.

### 참조 타입과 실제 타입의 차이

교안에서는 `Phone phone = new SmartPhoneImpl2(...)` 같은 코드가 등장한다. 참조 변수 타입은 `Phone`이지만 실제 객체는 `SmartPhoneImpl2`다.

이 상태에서 `phone.call()`을 하면 부모 메소드가 아니라 자식에서 `오버라이딩`한 메소드가 호출된다. 이 장면이 다형성의 핵심을 아주 직접적으로 보여 준다.

즉 "어떤 타입으로 바라보느냐"와 "실제로 어떤 객체가 들어 있느냐"를 분리해서 이해해야 한다는 뜻이다. 이 구분을 모르면 상속 구조는 금방 헷갈린다.

### 참조 타입 범위와 메소드 호출 제한

`phone.playMusic()`처럼 자식에만 있는 메소드는 상위 타입 참조 변수로는 바로 호출할 수 없다. 실제 인스턴스 안에 있다고 해도, 참조 타입 기준으로 보이는 범위가 다르기 때문이다.

이 제약은 불편해 보일 수도 있지만, 반대로 타입 안정성을 지켜 주는 장치이기도 하다. 상위 타입이 보장하는 공통 인터페이스 안에서 객체를 다루게 해 주기 때문이다.

#### `업캐스팅`, `다운캐스팅`, `instanceof` 코드 구조

```JAVA
Phone phone = new SmartPhoneImpl2("010-1234-5678", "Galaxy S");
phone.call(); // 실제 객체가 가진 오버라이딩 메소드가 실행된다.

if (phone instanceof SmartPhoneImpl2) {
    SmartPhoneImpl2 smartPhone = (SmartPhoneImpl2) phone;
    smartPhone.playMusic();
}
```

이 짧은 코드 안에 이번 주차 핵심이 거의 다 들어 있다. 참조 변수 타입은 `Phone`이지만 실제 객체는 `SmartPhoneImpl2`이고, 그래서 `call()`은 자식 쪽 메소드가 실행된다. 반대로 `playMusic()`처럼 자식 전용 기능을 쓰려면 `다운캐스팅` 전에 `instanceof`로 실제 타입을 먼저 확인해야 한다. 상속은 편리하지만, 타입을 정확히 보고 다뤄야 안전하다는 얘기가 바로 여기서 실감 난다.

## `형변환`과 `instanceof` 체크

업캐스팅은 자연스럽게 보이지만, 다운캐스팅은 늘 조심해야 한다. 이번 주차는 그 감각도 함께 정리해 준다.

### 업캐스팅과 다운캐스팅 주의점

`AndroidPhone`이나 `IPhone`을 `Phone`으로 받는 건 자동 형변환으로 자연스럽다. 하지만 다시 `IPhone`으로 내릴 때는 실제로 그 객체가 `IPhone`인지 확인해야 한다.

여기서 `instanceof`가 등장한다. 형변환이 가능한지 먼저 검사하고, 가능할 때만 다운캐스팅하는 흐름이다.

이 부분은 문법보다 태도에 가까웠다. 상속 구조를 믿되, 실제 객체가 무엇인지 확인하지 않은 채 섣불리 가정하지 않는 태도 말이다.

### `instanceof` 확인 절차

처음엔 `instanceof`가 예외를 피하기 위한 안전장치처럼만 보였는데, 이번 주차를 지나며 오히려 타입 관계를 코드 안에서 다시 확인하는 절차처럼 느껴졌다.

다형성을 쓰는 만큼, 어떤 객체가 들어올지 열어 두되 마지막 판단은 정확하게 하자는 방식이다.

## `다형성` 활용 예시

교안 후반의 `Application`, `GameAppImpl`, `UtilAppImpl`, `SmartPhoneImpl4` 예시는 이번 주차를 정리해 주는 느낌이 강했다.

### 상위 타입 배열과 앱 관리 구조

처음에는 게임 앱 배열, 유틸 앱 배열을 따로 두고 각각 설치 메소드를 따로 만드는 방식이 나온다. 그런데 다형성을 쓰면 `Application[] installedApps` 하나만으로도 서로 다른 앱을 함께 관리할 수 있다.

이 장면이 좋았던 이유는, 상속이 단지 부모 기능을 물려주는 수준을 넘어서 구조 전체를 단순하게 만들 수 있다는 점을 보여 줬기 때문이다.

### 상위 타입 중심 설계와 확장성

나중에 앱 종류가 하나 더 늘어나도 `Application`을 상속한 클래스라면 같은 방식으로 저장하고 설치하고 조회할 수 있다. 이게 다형성의 진짜 힘처럼 느껴졌다.

상위 타입 하나를 중심에 두고 다양한 하위 객체를 묶어 다룰 수 있다는 점이, 클래스 설계를 훨씬 확장 가능하게 만든다.

#### 배열과 컬렉션에서의 다형성

```JAVA
Application[] installedApps = new Application[3];

installedApps[0] = new GameAppImpl("Racing");
installedApps[1] = new UtilAppImpl("Calendar");
installedApps[2] = new GameAppImpl("Puzzle");

for (Application app : installedApps) {
    app.execute();
}
```

이 예시는 상속이 왜 "미래에 추가될 클래스"까지 염두에 둔 설계라고 하는지 잘 보여 준다. 배열 안에는 서로 다른 하위 클래스 객체가 들어가지만, 실행할 때는 `Application`이라는 공통 타입으로 한 번에 다룰 수 있다. 그래서 다형성은 설명으로 볼 때보다 코드로 볼 때 훨씬 납득이 잘 된다.

## 7주차 핵심 정리

이번 주차는 `상속`, `IS-A`, `HAS-A`, `super`, 생성자 호출, `오버라이딩`, 형변환, `instanceof`, `다형성`까지 이어지면서 객체지향에서 클래스 관계를 어떻게 읽어야 하는지 조금 더 분명하게 보여 줬다.

좋은 상속 구조는 부모 코드를 많이 재사용하는 구조가 아니라, 클래스 사이의 관계가 자연스럽고 확장 방향이 납득되는 구조라는 생각이 들었다. 그래서 상속은 편한 기능이라기보다 조심해서 써야 더 강한 도구에 가깝다.

## 중간고사 정리 포인트

중간고사 범위가 여기까지라면 7주차는 앞선 단원들을 이어 붙이는 역할이 크다. 초반에 배운 클래스와 객체 개념이 `상속`으로 확장되고, 6주차에 배운 `배열`도 `Application[]`처럼 다형성과 만나면서 훨씬 실전적인 구조로 바뀐다.

그래서 시험 준비를 할 때도 `상속`만 따로 외우기보다, `클래스 정의` → `객체 생성` → `배열` → `상속` → `다형성`으로 흐름을 묶어서 보는 편이 훨씬 잘 들어온다. 특히 `IS-A`와 `HAS-A`, `super`, `오버라이딩`, `업캐스팅/다운캐스팅`은 예제를 직접 손으로 따라가며 구분해 두는 게 좋겠다는 생각이 들었다.
