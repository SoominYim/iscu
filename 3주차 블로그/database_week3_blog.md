# [데이터베이스] 데이터베이스 학습 (3) - `DBMS`를 저장소라고만 보면 절반만 이해한 셈이다

`데이터베이스`를 처음 배우면 자꾸 "데이터를 모아 두는 곳"이라는 설명에 머무르게 된다. 틀린 말은 아니다. 하지만 이번 3주차 교안을 따라가다 보니, 그 설명만으로는 `데이터베이스 시스템`의 무게를 절반도 담아내지 못한다는 생각이 들었다. 실제로 중요한 건 저장 그 자체보다, **누가 어떤 구조로 데이터를 보고, 어떤 규칙으로 정의하고, 어떤 언어로 다루며, 어떤 책임으로 운영하느냐**에 더 가까웠기 때문이다.

이번 주차는 `데이터베이스`, `DBMS`, `스키마`, `인스턴스`, `3단계 스키마 구조`, `데이터 독립성`, `DBA`, `일반 사용자`, `응용 프로그래머`, `DDL`, `DML`, `DCL`, `TCL`, `절차형`, `비절차형` 언어까지 이어진다. 겉으로는 정의가 많은 단원처럼 보이지만, 정리하고 나면 오히려 서비스 개발 전체를 보는 눈이 조금 달라진다.

현업 프론트엔드 개발자 입장에서 이 단원이 중요한 이유도 분명하다. 화면은 결국 데이터를 어떻게 가져오고, 어떤 단위로 보여 주고, 어느 범위까지 수정할 수 있게 할지를 전부 데이터 구조 위에서 결정한다. 검색 조건이 왜 이렇게 생겼는지, 정렬 기준이 왜 제한되는지, 특정 정보가 어떤 화면에는 보이고 다른 화면에는 안 보이는지, 목록 조회가 왜 느린지 같은 문제는 대부분 `DBMS`와 데이터 모델의 세계에서 먼저 이유를 찾게 된다.

그래서 이번 주차는 데이터베이스를 "백엔드의 영역"으로만 두는 대신, **서비스 구조 전체를 지탱하는 기반 시스템**으로 다시 보게 만든 시간이었다.

## 1. 이번 단원에서 먼저 정리하고 싶었던 질문

3주차 교안을 읽기 전부터 머릿속에 있던 질문은 꽤 현실적이었다.

- `데이터베이스`와 `DBMS`는 왜 따로 구분해서 부를까?
- `스키마`와 `인스턴스`를 나누는 감각은 실제 개발에서 왜 중요할까?
- `외부 스키마`, `개념 스키마`, `내부 스키마`는 왜 굳이 세 단계로 나뉘어 있을까?
- 사용자 역할을 `DBA`, `응용 프로그래머`, `일반 사용자`로 구분하는 이유는 무엇일까?
- `SQL` 안에서 `DDL`, `DML`, `DCL`, `TCL`이 나뉘는 건 단순 분류일까, 아니면 책임 분담의 문제일까?

이 질문을 붙잡고 교안을 읽으니 용어 정리가 훨씬 실감 나게 들어왔다. 정의를 외우는 느낌보다, 시스템이 왜 이런 층위와 역할 분리를 필요로 하는지 이해하는 쪽에 더 가까웠다.

## 2. `데이터베이스 시스템`의 핵심은 데이터보다 관리 체계다

교안 초반부는 `데이터베이스 시스템`을 이루는 기본 요소를 차근차근 보여 준다. 여기서 가장 먼저 정리해야 할 건 `데이터베이스`와 `DBMS`를 같은 말처럼 섞어 쓰지 않는 습관이었다.

### 2.1. `데이터베이스`와 `DBMS`는 역할이 다르다

실무에서는 "DB에 넣는다", "DB에서 읽는다" 같은 표현이 너무 익숙해서 둘을 거의 구분하지 않게 된다. 그런데 교안은 이 둘을 아주 분명하게 갈라 둔다.

#### 2.1.1. `데이터베이스`는 내용물이고 `DBMS`는 운영 체계다

`데이터베이스`는 조직화된 데이터의 집합이다. 반면 `DBMS(Database Management System)`는 그 데이터를 정의하고, 저장하고, 검색하고, 수정하고, 보호하고, 여러 사용자가 함께 쓸 수 있게 관리하는 소프트웨어다. 즉, 데이터가 내용물이라면 `DBMS`는 그 내용을 안정적으로 다루게 하는 운영 체계에 가깝다.

이 차이는 생각보다 중요하다. 우리가 실제로 접속해서 명령을 보내고, 권한을 관리하고, 성능을 최적화하고, 백업과 복구를 논의하는 대상은 대부분 데이터 자체보다 `DBMS`이기 때문이다.

#### 2.1.2. 프론트엔드도 이 차이를 알아야 화면 해석이 쉬워진다

프론트엔드 개발자는 직접 `DBMS`를 다루지 않을 수 있다. 그렇다고 이 차이를 몰라도 된다는 뜻은 아니다. 예를 들어 어떤 목록은 필터가 풍부하고 어떤 목록은 필터가 제한적이라면, 그 차이는 보통 UI 디자이너의 취향보다 데이터 구조와 조회 방식에서 먼저 온다. 어떤 수정은 허용되고 어떤 수정은 제한되는 이유도 마찬가지다.

즉, 화면은 `API`를 통해 보이지만, 그 아래에서 실제 제약을 만드는 건 `DBMS`와 데이터 모델일 때가 많다. 이 감각이 있으면 프론트엔드도 요구사항을 더 현실적으로 읽게 된다.

### 2.2. `스키마`와 `인스턴스`를 구분하면 데이터가 더 입체적으로 보인다

이번 단원에서 가장 중요하게 남은 개념 중 하나가 `스키마`와 `인스턴스`의 차이였다.

#### 2.2.1. `스키마`는 구조이고 `인스턴스`는 현재 값이다

`스키마`는 데이터베이스의 구조, 타입, 제약 조건, 관계를 정의한 설계도다. 어떤 테이블이 있는지, 어떤 필드가 있는지, 어떤 형식을 따르는지, 서로 어떤 관계를 가지는지를 설명한다. 반면 `인스턴스`는 특정 시점에 실제로 저장된 데이터의 상태다.

쉽게 말하면 `스키마`는 양식이고 `인스턴스`는 그 양식에 채워진 내용이다. 환자 테이블의 컬럼 정의는 `스키마`이고, 지금 등록된 실제 환자 목록은 `인스턴스`다.

#### 2.2.2. 이 감각은 `API`와 타입 정의를 볼 때도 그대로 이어진다

프론트엔드 관점으로 바꾸면 더 익숙하다. `TypeScript`의 `interface`나 `OpenAPI` 명세는 일종의 `스키마`처럼 볼 수 있고, 실제 네트워크 응답은 `인스턴스`처럼 볼 수 있다. 이 둘을 섞어 생각하면 지금 바뀐 것이 "값"인지 "구조"인지 분간하기 어려워진다.

실무에서는 이 차이를 놓치면 협업이 꽤 힘들어진다. 어떤 팀은 단순 데이터 누락을 구조 문제처럼 받아들이고, 어떤 팀은 구조 변경을 일시적인 값 변경처럼 받아들인다. 결국 대화가 어긋난다. `스키마`와 `인스턴스`를 구분하는 언어 습관은 이런 혼선을 줄여 준다.

## 3. `3단계 스키마 구조`는 같은 데이터를 여러 시점에서 보기 위한 장치다

이번 단원에서 가장 데이터베이스답다고 느껴진 부분은 `외부 스키마`, `개념 스키마`, `내부 스키마`로 이어지는 `3단계 스키마 구조`였다. 처음엔 복잡해 보이지만, 정리하고 보면 굉장히 현실적인 모델이다.

### 3.1. `외부 스키마`는 사용자마다 다른 뷰를 허용한다

교안에서 `외부 스키마`는 특정 사용자나 응용 프로그램 관점에서 필요한 데이터만 보여 주는 외부 단계로 설명된다.

#### 3.1.1. 같은 데이터도 보는 사람에 따라 필요한 정보가 다르다

관리자 화면에서 필요한 사용자 정보와 일반 고객센터 화면에서 필요한 사용자 정보는 같지 않다. 어떤 화면에는 이메일과 권한 정보가 중요하고, 어떤 화면에는 주문 이력과 상태가 더 중요하다. 결국 모든 사용자에게 전체 데이터를 같은 형태로 보여 줄 수는 없다.

이게 바로 `외부 스키마` 감각이다. 같은 데이터베이스를 공유하더라도, 보는 관점과 필요한 정보 단위가 다를 수 있다는 사실을 구조 차원에서 인정하는 것이다.

#### 3.1.2. 화면 설계도 결국 `외부 스키마`와 닮아 있다

프론트엔드 입장에서 보면 이 개념은 더욱 익숙하다. 같은 회원 데이터를 다뤄도 마이페이지, 관리자 대시보드, 고객센터 툴, 마케팅 리포트 화면은 전부 다른 시점을 가진다. 결국 UI는 데이터의 전체 모습보다 **특정 역할에 맞춰 잘라 낸 관점**을 보여 주는 경우가 많다.

그래서 `외부 스키마`를 이해하면 "왜 어떤 화면은 이 필드가 있는데 저 화면은 없는가" 같은 질문에도 더 구조적으로 답할 수 있게 된다.

### 3.2. `개념 스키마`와 `내부 스키마`는 논리와 물리를 분리한다

`개념 스키마`는 조직 전체 수준의 논리적 데이터 구조를 설명하고, `내부 스키마`는 실제 저장 방식과 접근 경로 같은 물리적 구조를 다룬다.

#### 3.2.1. `개념 스키마`는 조직이 공유하는 데이터 언어다

사용자, 상품, 주문, 결제, 배송처럼 시스템의 핵심 엔티티를 어떤 관계로 정의할지 결정하는 층이 `개념 스키마`다. 이게 흔들리면 시스템 전체의 공통 언어가 흔들린다.

프론트엔드에서도 이 부분이 중요하다. 화면은 계속 늘어나도 중심 엔티티 정의는 어느 정도 일관되어야 한다. 사용자라는 개념이 화면마다 다르게 정의되고, 주문 상태가 API마다 다르게 해석되기 시작하면 기능이 많아질수록 혼란만 커진다.

#### 3.2.2. `내부 스키마`는 성능과 저장 효율을 책임진다

`내부 스키마`는 실제로 데이터가 어떻게 저장되고 어떤 접근 경로를 가지는지와 이어진다. 사용자는 직접 보지 않지만, 서비스 성능과 비용 구조에는 큰 영향을 준다. 그래서 `내부 스키마`는 논리 모델 아래에 숨은 현실 계층이라고 볼 수 있다.

이 지점이 인상적이었던 이유는, 데이터베이스가 결국 추상 이론이 아니라 **실제 물리 자원 위에서 돌아가는 시스템**이라는 감각을 다시 살려 줬기 때문이다.

### 3.3. `데이터 독립성`은 시스템을 오래 버티게 만드는 힘이다

교안은 `3단계 스키마 구조`를 설명하면서 `데이터 독립성`도 함께 다룬다. 이 개념은 이번 단원의 가장 실무적인 메시지 중 하나였다.

#### 3.3.1. 아래쪽 변화가 위쪽 코드를 무너뜨리지 않게 해야 한다

저장 방식이 조금 바뀌었다고 화면과 응용 프로그램 전부가 무너지면 시스템은 유지보수가 거의 불가능해진다. 반대로 어떤 사용자용 뷰가 추가되었다고 데이터 전체 구조를 뒤집어야 한다면 그것도 문제다. 결국 좋은 시스템은 계층별 변화가 서로를 완전히 직격하지 않도록 완충 장치를 가져야 한다.

이게 바로 `데이터 독립성`이 말하는 핵심이다. 물리적 변화와 논리적 변화가 위층의 모든 코드를 줄줄이 흔들지 않게 만드는 힘 말이다.

#### 3.3.2. 프론트엔드의 `adapter` 감각과도 닮아 있다

프론트엔드에서도 비슷한 일을 한다. 서버 응답 구조가 조금 바뀌더라도 UI 전체를 바로 뒤집지 않기 위해 `adapter`나 `mapper`를 두고, 도메인 모델과 화면 모델을 적당히 분리한다. 결국 좋은 아키텍처는 데이터베이스 쪽이든 프론트엔드 쪽이든 "변화를 어디서 흡수할 것인가"를 설계하는 일과 연결되어 있다.

## 4. 사용자와 언어를 보면 `DBMS`가 훨씬 더 현실적으로 다가온다

후반부로 가면 교안은 데이터베이스 사용자와 데이터베이스 언어를 설명한다. 이 부분이 좋았던 이유는, 데이터베이스가 단지 구조물이 아니라 **사람과 역할, 권한, 책임이 만나는 시스템**이라는 점을 선명하게 보여 주기 때문이다.

### 4.1. `DBA`, `응용 프로그래머`, `일반 사용자`는 서로 다른 문제를 푼다

데이터베이스를 사용하는 사람은 모두 같지 않다. 교안은 이를 역할별로 구분한다.

#### 4.1.1. `DBA`는 데이터를 넘어서 운영 신뢰성을 관리한다

`DBA(Database Administrator)`는 권한 관리, 보안, 무결성, 백업, 복구, 성능, 전체 정책을 책임진다. 즉, 데이터를 넣고 빼는 역할이 아니라 **데이터 환경이 안정적으로 유지되도록 만드는 역할**에 가깝다.

이걸 보며 느낀 건, 서비스 품질은 보이는 화면만으로 결정되지 않는다는 점이었다. 사용자가 체감하는 응답 속도나 장애 복구 속도, 접근 제어 수준도 결국 이런 역할이 뒤에서 받쳐 줘야 유지된다.

#### 4.1.2. `응용 프로그래머`와 `일반 사용자`는 같은 데이터를 다르게 만난다

응용 프로그래머는 기능을 만들기 위해 데이터를 다루고, 일반 사용자는 일상적인 업무 수행을 위해 데이터를 사용한다. 둘 다 같은 데이터베이스와 닿지만, 보는 관점과 책임은 전혀 다르다.

프론트엔드 개발자는 직접 SQL을 치지 않더라도, 결국 사용자와 데이터 사이의 접점을 설계하는 사람이다. 어떤 정보가 보이고, 어떤 행위가 가능하고, 어떤 오류가 드러나는지를 결정한다는 점에서, 데이터 사용자 역할의 바깥에 서 있다고 보기는 어렵다.

### 4.2. `DDL`, `DML`, `DCL`, `TCL`은 SQL을 역할별로 나눈 결과다

교안에서 가장 실용적이었던 부분 중 하나는 `데이터베이스 언어`를 기능별로 나눠 보여 준 부분이었다. `SQL`을 한 덩어리로만 보지 않고, 각각의 책임으로 나누어 이해하게 만든다.

#### 4.2.1. `DDL`과 `DML`은 구조와 데이터라는 서로 다른 층을 다룬다

`DDL(Data Definition Language)`은 `CREATE`, `ALTER`, `DROP`처럼 구조를 정의하고 바꾸는 언어다. 반면 `DML(Data Manipulation Language)`은 `SELECT`, `INSERT`, `UPDATE`, `DELETE`처럼 실제 데이터를 다루는 언어다.

이 구분이 중요한 이유는, 구조를 바꾸는 일과 데이터를 조작하는 일의 파급력이 다르기 때문이다. 어떤 컬럼을 없애거나 추가하는 건 시스템 전체에 영향을 줄 수 있지만, 특정 데이터를 조회하거나 수정하는 것은 그보다 더 좁은 범위의 행위일 수 있다.

프론트엔드 관점에서도 이 차이는 중요하다. 대부분의 화면은 `DML` 결과를 소비하지만, 새로운 기능이 생길 때 그 뒤에서 `DDL` 수준의 변경이 필요할 수도 있다. 즉, 프론트엔드가 직접 `DDL`을 쓰지 않더라도 그 영향은 충분히 받는다.

#### 4.2.2. `DCL`과 `TCL`은 신뢰성과 운영 통제를 담당한다

`DCL(Data Control Language)`은 권한을 다루고, `TCL(Transaction Control Language)`은 `COMMIT`, `ROLLBACK`, `SAVEPOINT`처럼 트랜잭션 흐름을 제어한다. 이 둘은 사용자가 직접 보지 않아도 시스템 신뢰성에는 매우 중요하다.

특히 결제, 예약, 재고, 정산처럼 데이터 일관성이 핵심인 기능에서는 `TCL` 감각이 필수적이다. 프론트엔드도 이 흐름을 이해하고 있어야 실패 시 어떤 메시지를 보여 줄지, 낙관적 업데이트를 어디까지 허용할지, 재시도 UX를 어떻게 설계할지 더 나은 판단을 할 수 있다.

## 5. 이번 단원을 지나며 남은 건 "데이터는 구조와 역할 안에서 살아 움직인다"는 감각이었다

이번 3주차 `데이터베이스 시스템` 파트는 겉으로는 용어가 많은 단원이었다. 하지만 끝까지 정리하고 나니 핵심은 생각보다 명확했다. 결국 중요한 건 데이터 한 덩어리가 아니라, **그 데이터를 어떤 구조로 정의하고, 누가 어떤 시점에서 보고, 어떤 언어로 다루며, 어떤 책임 아래 운영하는가**였다.

프론트엔드 개발자로서도 이번 단원은 충분히 공부가 됐다. 화면은 데이터의 마지막 표현일 뿐이고, 그 전에 이미 `스키마`, `DBMS`, 사용자 역할, 쿼리 언어, 권한 구조, 트랜잭션 규칙이 훨씬 더 깊은 층에서 움직이고 있다는 걸 다시 보게 됐기 때문이다. 결국 좋은 화면을 만들기 위해서도 데이터베이스를 "백엔드가 관리하는 창고" 정도로만 보면 안 되고, **서비스 전체의 질서를 만드는 기반 시스템**으로 이해해야 한다는 생각이 더 강하게 남았다.
