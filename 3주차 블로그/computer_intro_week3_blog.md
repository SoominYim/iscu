# [컴퓨터개론] 컴퓨터개론 학습 (3) - `하드웨어`를 알면 성능 이야기가 훨씬 덜 추상적이 된다

프론트엔드 개발을 오래 할수록 자꾸 브라우저 안쪽 세계에 익숙해진다. `React`, `JavaScript`, `Network`, `Rendering`, `Bundle`, `Hydration` 같은 단어는 일상처럼 쓰는데, 정작 이 모든 게 실제로 어떤 `하드웨어` 위에서 돌아가는지에 대해서는 흐릿해지기 쉽다. 코드를 짜는 데 당장 `메인보드`나 `버스` 구조를 몰라도 되니까 더 그렇다. 그런데 성능 이슈를 오래 파거나, 로딩 지연과 메모리 사용량, 입출력 병목 같은 문제를 붙잡고 있으면 결국 다시 하드웨어 쪽 감각으로 돌아오게 된다.

이번 3주차 `컴퓨터개론` 교안은 바로 그 바닥을 다시 보게 해 줬다. `메인보드`, `버스`, `폰노이만 구조`, `RAM`, `ROM`, `HDD`, `SSD`, 주변장치와 `포트`, `인터럽트`, `DMA`, `버퍼`, `멀티프로세싱`, `멀티코어`, `명령어 병렬 처리`까지 흐름이 꽤 넓게 이어진다. 처음에는 범위가 넓어서 산만하게 느껴질 수도 있다. 그런데 정리하고 나면 오히려 한 가지 질문으로 수렴한다. **컴퓨터는 왜 역할을 이렇게 잘게 나눠 두고 협력하도록 설계되었을까?**

현업 프론트엔드 개발자 입장에서 이번 단원이 좋았던 이유는, 화면 밖의 세계를 조금 더 구체적으로 상상하게 해 줬기 때문이다. 우리가 만드는 UI는 결국 `CPU`, `메모리`, 저장장치, 입출력 장치, 운영체제, 브라우저가 함께 움직인 결과물이다. 그러니 성능을 더 잘 이해하고 싶다면 추상 레벨 높은 코드만 볼 게 아니라, 그 코드가 실제로 어떤 자원을 지나가며 실행되는지도 같이 떠올릴 수 있어야 한다.

## 1. 이번 단원에서 먼저 붙잡은 질문

교안을 읽기 전에 가장 먼저 정리하고 싶었던 질문은 다음과 같았다.

- 왜 컴퓨터는 `CPU`, `메모리`, 입출력 장치를 굳이 분리해서 관리할까?
- `주소 버스`, `데이터 버스`, `제어 버스`를 나누는 이유는 무엇일까?
- `RAM`과 저장장치를 구분하는 감각은 지금도 왜 중요한가?
- `인터럽트`, `DMA`, `버퍼`는 왜 성능 설명에서 자꾸 함께 등장할까?
- `멀티프로세싱`과 `멀티코어`를 이해하면 소프트웨어 성능을 보는 시선도 달라질까?

이 질문을 가지고 보니, 하드웨어 부품 설명이 단순 명칭 암기가 아니라 **정보가 이동하고 처리되고 저장되는 전체 흐름을 이해하는 작업**처럼 읽혔다.

## 2. 컴퓨터는 왜 이렇게 역할을 나눠 놓았을까

교안 초반은 컴퓨터 시스템의 기본 구성과 `메인보드`를 중심으로 한 연결 구조를 설명한다. 이 파트의 핵심은 부품 이름을 외우는 게 아니라, 서로 다른 역할을 가진 장치들이 어떻게 협력하는지 보는 데 있다.

### 2.1. `메인보드`는 부품을 꽂는 판이 아니라 연결 구조의 중심이다

`메인보드`를 단순히 부품이 붙는 큰 보드라고 생각하면 이 부분은 밋밋하게 보일 수 있다. 하지만 교안을 따라가 보면, `메인보드`는 실제로 각 장치가 정보를 주고받을 수 있도록 이어 주는 중심 연결판에 가깝다.

#### 2.1.1. `버스`는 결국 장치 사이의 길이다

교안은 `버스`를 `주소 버스`, `데이터 버스`, `제어 버스`로 나눠 설명한다. 이 구분은 생각보다 직관적이다.

- `주소 버스`는 어디로 갈지를 지정한다.
- `데이터 버스`는 실제 데이터를 옮긴다.
- `제어 버스`는 읽기와 쓰기, 신호 타이밍, 동작 제어를 담당한다.

이렇게 나누는 이유는 분명하다. 컴퓨터 안에서는 "무엇을 보낼지", "어디로 보낼지", "어떤 방식으로 처리할지"가 동시에 필요하기 때문이다. 길 하나에 모든 의미를 한꺼번에 싣는 대신 역할을 분리해 둬야 흐름이 안정된다.

#### 2.1.2. 이 구조는 소프트웨어 아키텍처 감각과도 닮아 있다

이 설명을 보면서 프론트엔드에서 자주 하는 일들이 떠올랐다. 실제 데이터만 있다고 시스템이 돌아가지 않는다. 대상 식별자와 상태, 명령 신호와 결과 데이터가 적절히 분리되어야 흐름이 덜 꼬인다. 결국 하드웨어든 소프트웨어든 **역할을 분리해서 연결하는 구조**가 안정성을 만든다는 점에서 닮아 있다.

### 2.2. `폰노이만 구조`가 지금도 유효한 이유

교안은 `폰노이만 구조`도 함께 다룬다. 명령어와 데이터를 메모리에 저장하고, `CPU`가 이를 순서대로 읽어 처리하는 구조다. 아주 오래된 개념처럼 느껴질 수 있지만, 여전히 기본 뼈대로 기능한다.

#### 2.2.1. 프로그램도 결국은 메모리에 올라간 데이터다

이 설명이 중요한 이유는, 프로그램과 데이터가 완전히 다른 세계가 아니라는 점을 보여 주기 때문이다. 스크립트 코드도, 이미지 경로도, 네트워크 응답도, 실행 중인 상태값도 결국 메모리 안에서 읽히고 쓰인다. 브라우저에서 우리가 보는 화면도 이 구조 위에서 작동한다.

#### 2.2.2. 추상화가 높을수록 바닥 구조를 잊기 쉬워진다

프레임워크를 오래 쓰다 보면 "코드가 실행된다"는 감각이 지나치게 추상적으로 변할 때가 있다. 하지만 렌더링 병목, 메모리 누수, 긴 작업 블로킹 같은 문제를 파고들면 결국 다시 하드웨어와 실행 구조를 떠올리게 된다. 그래서 `폰노이만 구조` 같은 기본 개념은 오래된 이론이 아니라, **추상화 아래에서 실제 실행이 어떻게 일어나는지 떠올리게 해 주는 기준점**처럼 느껴졌다.

## 3. 저장장치와 입출력을 보면 왜 체감 성능이 달라지는지 더 잘 보인다

중반부 교안은 `RAM`, `ROM`, `HDD`, `SSD`, 주변장치, `포트` 설명으로 이어진다. 이 부분이 실용적인 이유는 사용자가 느끼는 "빠름"과 "느림"이 대부분 이런 자원 차이에서 바로 드러나기 때문이다.

### 3.1. `RAM`, `ROM`, `HDD`, `SSD`는 모두 저장이지만 같은 저장이 아니다

처음에는 전부 비슷한 저장 공간처럼 느껴지지만, 실제 역할은 꽤 다르다.

#### 3.1.1. `RAM`은 실행 중인 일을 붙잡고 있는 작업 공간이다

`RAM`은 휘발성 메모리다. 전원이 꺼지면 내용이 사라지지만, 실행 중인 프로그램과 현재 작업 데이터를 빠르게 올려 두는 공간으로 쓰인다. 즉, 속도를 위해 존재하는 실시간 작업 공간에 가깝다.

브라우저 탭을 많이 열면 메모리 사용량이 커지고, 무거운 페이지를 여러 개 띄우면 시스템이 버벅이는 이유도 여기와 연결된다. 프론트엔드 개발자가 성능을 보다가 결국 메모리 점유율을 확인하게 되는 이유도 이 때문이다.

#### 3.1.2. `HDD`와 `SSD` 차이는 개발 경험에도 꽤 직접적이다

교안에서 `HDD`와 `SSD`를 구분해 설명하는 부분도 좋았다. `HDD`는 기계적으로 읽고 쓰는 저장장치이고, `SSD`는 반도체 기반이라 접근 속도가 훨씬 빠르다. 이 차이는 단순 이론이 아니라 부팅 속도, 프로그램 실행 속도, 파일 열기 속도에서 바로 체감된다.

개발 환경으로 가져오면 더 현실적이다. 프로젝트 설치, 빌드 캐시 읽기, 이미지 처리, 테스트 실행, 개발 서버 시작 속도도 모두 저장장치 영향을 받는다. 그래서 "내 코드가 느린가?"라고 생각한 문제가 사실은 디스크 입출력 병목인 경우도 적지 않다.

### 3.2. `포트`와 주변장치는 컴퓨터가 바깥과 만나는 접점이다

교안의 `포트` 파트는 단순 단자 종류 소개처럼 보이지만, 사실은 컴퓨터가 외부 세계와 데이터를 주고받는 실제 문이다.

#### 3.2.1. 입력장치와 출력장치는 모두 다른 속도로 움직인다

키보드, 마우스, 모니터, 저장장치, 네트워크 장비는 모두 컴퓨터와 다른 방식으로 상호작용한다. 어떤 장치는 아주 작은 이벤트를 자주 보내고, 어떤 장치는 큰 데이터 덩어리를 천천히 전달한다. 결국 이 다양한 흐름을 안정적으로 연결해 주는 물리적 접점이 `포트`와 주변 인터페이스다.

#### 3.2.2. 프론트엔드는 결국 이 입출력 흐름의 맨 끝에서 경험으로 드러난다

우리가 만드는 UI는 사용자가 키보드를 누르고, 터치를 하고, 화면을 보고, 소리를 듣는 경험으로 드러난다. 즉, 프론트엔드 코드는 브라우저 안에 있지만 결과적으로는 주변장치와 사용자의 상호작용 위에서 의미를 가진다. 이런 점에서 입출력 장치를 이해하는 건 UI 경험을 더 물리적으로 상상하게 만든다.

## 4. 시스템 성능을 이해하려면 `인터럽트`, `DMA`, `버퍼`, `멀티프로세싱`까지 같이 봐야 한다

후반부 교안은 단순한 부품 소개를 넘어, 장치들이 서로 다른 속도로 움직일 때 컴퓨터가 어떻게 조율하는지를 설명한다. 여기서부터 성능 이야기가 훨씬 살아난다.

### 4.1. `인터럽트`, `DMA`, `버퍼`는 속도 차이를 흡수하기 위한 장치다

`CPU`는 매우 빠르고, 외부 장치는 상대적으로 느리다. 이 속도 차이를 그대로 두면 시스템 전체가 비효율적으로 움직일 수밖에 없다. 교안은 이 문제를 해결하는 핵심 개념으로 `인터럽트`, `DMA`, `버퍼`를 보여 준다.

#### 4.1.1. `인터럽트`는 계속 감시하지 않기 위한 신호 체계다

`인터럽트`는 장치가 CPU에게 "지금 처리할 일이 생겼다"고 알려 주는 방식이다. 이 구조 덕분에 CPU는 모든 장치를 계속 폴링할 필요 없이, 필요한 순간에만 반응할 수 있다.

이 개념은 브라우저 이벤트 모델과도 묘하게 닮아 있다. 클릭과 입력, 네트워크 완료, 타이머 종료가 발생했을 때만 콜백이 실행되는 구조처럼, 하드웨어도 모든 걸 매순간 감시하기보다 이벤트 기반으로 반응하는 쪽이 더 효율적이다.

#### 4.1.2. `DMA`와 `버퍼`는 시스템 전체를 덜 막히게 만든다

`DMA(Direct Memory Access)`는 CPU를 거치지 않고 장치와 메모리 사이에서 데이터를 전송하게 해 준다. `버퍼`는 속도가 다른 장치 사이의 간격을 흡수하는 임시 공간이다. 교안이 이 둘을 함께 설명하는 이유도 명확하다. 결국 둘 다 **가장 느린 부분 때문에 전체 흐름이 멈추지 않게 만드는 장치**이기 때문이다.

프론트엔드 관점으로 바꾸면, 이건 디바운스, 스로틀, 스트리밍 처리, 가상 스크롤, 이미지 프리로드처럼 사용자 체감 흐름을 부드럽게 만들기 위한 완충 장치들과도 닮아 있다. 표현은 다르지만 사고방식은 꽤 비슷하다.

### 4.2. `멀티프로세싱`과 `멀티코어`는 왜 계속 중요할까

교안 후반의 `멀티프로세싱`, `멀티코어`, `명령어 병렬 처리` 설명은 성능을 바라보는 관점을 더 넓혀 준다. 단일 프로세서로 모든 일을 순차 처리하던 시대와, 여러 코어가 동시에 작업을 나누는 시대는 소프트웨어 설계에도 영향을 준다.

#### 4.2.1. 빠른 컴퓨터는 결국 일을 잘 나누는 컴퓨터이기도 하다

`멀티프로세서 시스템`과 `멀티코어 시스템`의 설명을 따라가면 핵심은 분명해진다. 하나의 빠른 처리 장치만으로 모든 일을 해결하기보다, 나눌 수 있는 작업은 나눠서 동시에 처리하는 편이 전체 효율이 높다.

물론 병렬화가 항상 쉬운 건 아니다. 공유 자원 충돌, 동기화 비용, 작업 분할 오버헤드가 있기 때문이다. 그래서 멀티코어 시대의 성능은 "코어 수가 많다"보다 **일감을 어떻게 나누고 묶는가**에 더 가까운 문제처럼 느껴졌다.

#### 4.2.2. 프론트엔드도 결국 메인 스레드의 한계를 계속 만난다

브라우저를 떠올리면 이 개념은 더 현실적이다. 렌더링, 자바스크립트 실행, 레이아웃 계산, 페인팅이 메인 스레드에 몰리면 UI는 금방 버벅인다. 그래서 `Web Worker`를 쓰거나, 무거운 계산을 비동기로 분리하거나, 렌더링 횟수를 줄이고, 이미지와 데이터 처리 시점을 조절하는 식의 전략이 필요해진다.

즉, 하드웨어의 `멀티코어` 구조를 아는 게 곧 프론트엔드 최적화 정답을 주는 건 아니지만, 적어도 왜 메인 스레드 블로킹이 위험한지, 왜 일부 작업을 분리해야 하는지 훨씬 설득력 있게 이해하게 해 준다.

## 5. 이번 단원을 지나며 남은 건 "성능은 코드만의 문제가 아니다"라는 감각이었다

이번 3주차 `컴퓨터개론`은 부품 이름을 정리하는 단원처럼 보였지만, 정리하고 나니 훨씬 더 넓은 이야기를 하고 있었다. `메인보드`, `버스`, `메모리`, 저장장치, 입출력 장치, `인터럽트`, `버퍼`, `멀티코어`는 각각 따로 존재하는 개념이 아니라, 서로 속도와 역할이 다른 자원들이 어떻게 협력해야 시스템 전체가 매끄럽게 움직이는지를 설명하는 조각들이었다.

프론트엔드 개발자로서도 이번 단원은 꽤 도움이 됐다. 화면 성능을 더 잘 이해하고 싶다면, 자바스크립트 코드만 들여다보는 것에서 한 걸음 더 나아가 그 코드가 실제로 `CPU`, `RAM`, 저장장치, 브라우저의 스레드 구조 위에서 어떻게 소비되는지 상상할 수 있어야 한다는 생각이 더 선명해졌기 때문이다. 결국 좋은 성능 감각은 추상화 위에서만 생기지 않고, **그 아래를 받치고 있는 하드웨어 흐름을 함께 볼 때 더 단단해진다**는 점이 이번 주차의 가장 큰 수확이었다.
