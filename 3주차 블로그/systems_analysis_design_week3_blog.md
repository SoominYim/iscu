# [시스템분석및설계] 시스템분석및설계 학습 (3) - `요구분석`이 흔들리면 좋은 화면도 오래 못 간다

프로젝트가 꼬이기 시작하는 지점은 생각보다 늦지 않다. 구현이 한참 진행된 뒤가 아니라, 오히려 가장 초반에 이미 방향이 어긋난 채 출발하는 경우가 많다. 기능 이름은 정해졌는데 실제 사용 맥락은 모호하고, 고객은 "간단하게"를 말하는데 업무 규칙은 복잡하고, 속도가 중요하다고 하면서 정확히 어느 정도 속도를 원하는지는 정리되지 않은 상태. 이렇게 시작하면 화면은 만들어져도 프로젝트는 계속 다시 돌아가게 된다.

이번 3주차 `시스템분석및설계` 교안의 중심은 바로 이 지점이다. 주제는 `요구분석`. 사용자 참여, 요구분석 과정, `문제정의`와 `요구사항 정의`의 차이, `기능 요구`와 `비기능 요구`, 문제 구조화, `로직 트리`, `MECE`, 업무 프로세스 분석, `BPMN`, 해결책 도출, `To-Be` 시뮬레이션까지 흐름이 꽤 탄탄하다. 단순히 문서를 잘 쓰는 법을 배우는 게 아니라, **왜 개발이 자꾸 빗나가는지 초반 원인을 추적하는 과목**처럼 느껴졌다.

현업 프론트엔드 개발자로 일하다 보면 이 단원이 더 실감 난다. 요구가 애매하면 가장 먼저 흔들리는 게 화면이다. 어떤 데이터를 보여 줘야 하는지, 어떤 액션을 허용해야 하는지, 오류는 어디까지 안내해야 하는지, 응답 속도는 어느 수준이어야 하는지 같은 문제가 전부 UI와 직접 연결되기 때문이다. 결국 `요구분석`은 백로그를 예쁘게 정리하는 절차가 아니라, **나중에 화면과 기능이 덜 흔들리게 만드는 첫 번째 설계 작업**에 가깝다.

## 1. 이번 단원에서 먼저 정리하고 싶었던 문제의식

이번 3주차를 읽기 전에 머릿속에서 계속 돌던 질문은 다음과 같았다.

- 왜 `요구분석`은 중요하다고 다들 말하면서도 현장에서는 자주 압축되거나 생략될까?
- 고객이 말한 요구와 시스템이 실제로 구현해야 할 요구는 왜 다를까?
- `기능 요구`만 정리하면 안 되고 `비기능 요구`까지 따로 봐야 하는 이유는 무엇일까?
- 문제를 구조화한다는 건 구체적으로 어떤 작업을 말할까?
- `To-Be` 프로세스를 그리는 일은 왜 문서 작업이 아니라 실질적인 설계 행위일까?

이 질문들을 먼저 세워 두고 교안을 보니, 이번 주차는 개념 암기보다 "프로젝트가 어긋나는 이유를 언어로 설명하는 법"에 더 가까웠다.

## 2. `요구분석`은 요청을 받아 적는 일이 아니라 문제를 공동으로 정의하는 일이다

교안 초반에서 가장 먼저 강조하는 건 요구분석에 사용자와 관련자의 참여가 반드시 필요하다는 점이다. 이 말이 왜 그렇게 중요한지, 실무를 떠올리면 금방 이해된다.

### 2.1. 사용자 참여가 빠지면 요구는 쉽게 공중에 뜬다

개발사는 시스템을 어떻게 구성해야 안정적이고 효율적인지 잘 안다. 하지만 고객의 업무 맥락, 실제 현장의 예외, 사용자가 매일 어디서 불편함을 느끼는지까지 완전히 알 수는 없다. 반대로 고객은 자신의 문제를 잘 알지만, 그것을 시스템 요구사항으로 번역하는 방법은 익숙하지 않을 수 있다.

#### 2.1.1. 개발사는 기술을 알고, 사용자는 맥락을 안다

이 문장을 단순하게 보지 않게 된 이유는, 실제 프로젝트에서 이 둘이 분리될 때 문제가 금방 커지기 때문이다. 개발사는 구현 가능한 구조를 제안할 수 있지만, 현업의 예외 흐름을 놓칠 수 있다. 사용자는 불편을 정확히 느끼지만, 그것을 기능과 품질 기준으로 분리해 말하기 어려울 수 있다.

결국 `요구분석`은 한쪽이 정답을 말하고 다른 쪽이 받아 적는 단계가 아니라, 서로 다른 관점을 가진 사람들이 **같은 문제를 같은 언어로 다시 정의하는 협업 과정**이 된다.

#### 2.1.2. 프론트엔드는 이 충돌을 가장 빨리 체감하는 위치에 있다

요구가 정리되지 않았을 때 가장 먼저 복잡해지는 건 종종 화면이다. 예를 들어 고객은 "주문 화면이 간단했으면 좋겠다"고 말하지만, 실제로는 승인 단계가 여러 개고, 주문 조건별로 다른 입력이 필요하고, 오류 케이스도 다양하다면 UI는 순식간에 무거워진다.

그래서 프론트엔드 개발자는 단순히 주어진 요구를 구현하는 사람으로만 남기 어렵다. 화면 흐름을 설계하다 보면, 자연스럽게 "이 요구는 아직 명확하지 않다", "예외 케이스가 빠져 있다", "비기능 기준이 비어 있다"는 걸 먼저 발견하게 된다. 그런 점에서 `요구분석` 감각은 프론트엔드에게도 아주 실무적인 능력이다.

### 2.2. `문제정의`와 `요구사항 정의`는 분명히 다른 단계다

이번 교안에서 특히 좋았던 건 `문제정의`와 `요구사항 정의`를 명확하게 분리해 설명한 부분이다. 이 차이를 놓치면 프로젝트 초반 대화가 계속 공중에 뜨기 쉽다.

#### 2.2.1. `문제정의`는 거칠어도 괜찮은 출발점이다

`문제정의`는 고객이 느끼는 불편, 현재 프로세스의 문제, 해결하고 싶은 방향을 담은 단계다. 교안에서도 여기에는 중복, 누락, 모순이 있어도 괜찮다고 설명한다. 왜냐하면 아직은 "무엇이 문제인가"를 드러내는 단계이지, 시스템이 구현할 내용을 완성된 문장으로 정리하는 단계는 아니기 때문이다.

실무에서도 이 구간은 늘 거칠다. "사용자가 더 빨리 찾았으면 좋겠다", "관리자가 수작업을 덜 했으면 좋겠다", "승인 과정이 너무 복잡하다", "조회가 자꾸 느리다" 같은 말은 중요하지만, 아직 구현 항목으로는 충분하지 않다.

#### 2.2.2. `요구사항 정의`는 시스템이 이해할 수 있는 형태로 다시 쓰는 일이다

그다음이 `요구사항 정의`다. 여기서는 문제를 기반으로 실제 구현 가능한 항목을 정리한다. 즉, 중복을 제거하고, 빠진 조건을 보완하고, 모순을 줄이고, 문서를 기준으로 삼을 수 있을 만큼 정교한 상태로 바꾸는 과정이다.

이 차이를 이해하고 나니 왜 요구분석에 시간이 필요한지 더 잘 보였다. 문제를 발견하는 일과, 그 문제를 시스템의 입력으로 변환하는 일은 전혀 같은 작업이 아니다. 결국 `요구사항 정의`는 고객의 말을 잘 듣는 능력뿐 아니라, **그 말을 구조화된 시스템 요구로 번역하는 능력**까지 같이 요구한다.

## 3. `기능 요구`와 `비기능 요구`를 나누는 순간 품질 얘기가 가능해진다

이번 주차에서 가장 실무적인 파트 하나를 꼽으라면 단연 `기능 요구`와 `비기능 요구`를 구분하는 부분이다. 많은 프로젝트가 기능 목록은 정리하지만, 품질 기준은 모호하게 두고 넘어가서 나중에 훨씬 큰 재작업을 만든다.

### 3.1. `기능 요구`는 시스템이 해야 할 일을 정의한다

교안은 `기능 요구`를 시스템이 제공해야 할 처리와 서비스라고 설명한다. 고객 등록, 주소 검색, 상품 조회, 주문 처리, 장바구니 저장, 후기 작성 같은 항목이 여기에 해당한다.

#### 3.1.1. 기능 목록은 화면 설계의 출발점이지만 도착점은 아니다

프론트엔드 관점에서 `기능 요구`는 보통 화면과 액션 단위로 번역된다. 어떤 버튼이 필요한지, 어떤 입력 필드를 둬야 하는지, 어떤 목록과 상세 페이지가 필요한지, 어떤 상태 변화가 일어나야 하는지 같은 질문이 여기서 출발한다.

하지만 기능 목록만으로는 화면이 완성되지 않는다. "검색 기능이 필요하다"는 한 줄만으로는 검색 조건이 몇 개인지, 자동완성이 필요한지, 빈 결과 처리 방식은 어떤지, 모바일에서는 어떻게 줄여 보여야 하는지, 접근성은 어떻게 맞출지 전혀 알 수 없다. 즉, 기능 요구는 출발점이지 완성본이 아니다.

#### 3.1.2. 쇼핑몰 사례가 현실적으로 와닿는 이유

교안에서 든 쇼핑몰 예시는 그래서 꽤 좋았다. 상품 열람, 주문, 배송 상태 확인, 후기 작성, 회원 정보 보관, 장바구니, 마일리지 기능처럼 매우 익숙한 기능을 예로 들고 있는데, 이 예시는 동시에 "기능 목록이 많다고 곧장 좋은 시스템이 되는 건 아니다"는 사실도 같이 보여 준다.

서비스는 기능이 많을수록 좋은 게 아니라, 기능이 사용자 시나리오 안에서 일관되게 이어질 때 좋아진다. 그리고 이 일관성을 만드는 출발점이 바로 기능 요구 정리다.

### 3.2. `비기능 요구`는 시스템의 체감 품질을 정한다

교안은 `비기능 요구`를 응답 속도, 보안, 신뢰성, 사용성, 호환성, 가동성 같은 품질 특성과 연결해 설명한다. 이 부분이 특히 중요하게 느껴진 이유는, 사용자가 실제로 "좋다", "별로다"를 판단하는 지점 대부분이 여기에 있기 때문이다.

#### 3.2.1. 기능이 있어도 `비기능 요구`가 비면 서비스는 쉽게 무너진다

검색 기능은 있는데 5초씩 걸리면 사용자는 그 기능을 좋은 기능이라고 느끼지 않는다. 결제 기능은 있는데 오류 메시지가 부정확하면 신뢰가 떨어진다. 목록은 보이는데 모바일에서 레이아웃이 깨지면 사용성은 급격히 낮아진다.

즉, `비기능 요구`는 기능이 아닌 부가조건이 아니라, **기능이 실제로 받아들여질 수 있게 만드는 실행 조건**에 가깝다.

#### 3.2.2. 프론트엔드가 놓치기 쉬운 것도 대부분 여기다

프론트엔드 개발을 하다 보면 다음과 같은 문제를 자주 만난다.

- 기능은 있는데 반응 속도가 느리다.
- 오류 안내는 나오지만 사용자가 다음 행동을 알 수 없다.
- 화면은 완성됐는데 접근성이 충분하지 않다.
- 데스크톱에서는 멀쩡한데 모바일 환경에서는 깨진다.
- 사용자는 많은데 렌더링 성능이 버티지 못한다.

이 문제들은 기능이 부족해서가 아니라, `비기능 요구`를 초반에 충분히 정의하지 않았기 때문에 생기기 쉽다. 그래서 이번 단원은 "품질은 구현 마지막에 챙기는 옵션이 아니다"라는 사실을 꽤 분명하게 남긴다.

## 4. 문제를 구조화하고 프로세스를 그려야 해결책이 비로소 보인다

교안 후반부는 요구사항 분류에서 멈추지 않고, 문제를 더 깊게 분석하는 방법으로 넘어간다. 이 흐름이 특히 좋았다. 요구를 많이 적는다고 분석이 되는 게 아니라, **문제를 어떻게 쪼개고 어떤 흐름으로 이해할지**가 중요하다는 걸 보여 주기 때문이다.

### 4.1. `로직 트리`와 `MECE`는 생각을 정리하는 도구다

문제를 구조화하는 도구로 교안은 `로직 트리`와 `MECE`를 제시한다. 처음에는 조금 컨설팅스럽게 들리지만, 실제 회의 상황을 떠올리면 왜 필요한지 금방 이해된다.

#### 4.1.1. 좋은 분해는 원인을 선명하게 만들고, 나쁜 분해는 논의를 흐린다

`MECE`는 서로 겹치지 않으면서 전체를 빠짐없이 포괄하는 분해 원리다. 교안에서 든 예시처럼 카테고리가 서로 겹치거나 기준이 섞이면, 문제의 원인을 찾기도 전에 논의가 먼저 흐려진다.

예를 들어 "심각한 오류", "기술적 문제", "사용자 불만", "성능 문제"처럼 한 표에 올려놓으면 항목이 서로 중첩되고 분류 기준도 섞인다. 반면 서버, 네트워크, 스토리지, 보안 인프라처럼 같은 축으로 나누면 원인을 추적하기 쉬워진다.

#### 4.1.2. 회의가 길어지는 팀은 대체로 분해 기준이 흔들린다

실무에서도 회의가 끝나지 않는 팀을 보면 자주 이 문제가 보인다. 어떤 사람은 화면 단위로 말하고, 어떤 사람은 기능 단위로 말하고, 어떤 사람은 담당 조직 기준으로 말한다. 그러면 모두가 같은 문제를 말한다고 생각하면서도 사실은 다른 분류 체계 위에서 대화하게 된다.

그래서 `로직 트리`와 `MECE`는 예쁜 문서 도구가 아니라, **서로 다른 사람의 사고 방향을 한 축으로 맞추는 실무 도구**라고 보는 편이 더 정확하다.

### 4.2. `업무 프로세스 분석`과 `To-Be` 설계는 구현 전의 진짜 설계다

교안은 이어서 `업무 프로세스 분석`, `BPMN`, 해결책 도출, `To-Be` 프로세스 시뮬레이션을 설명한다. 이 부분이 이번 단원을 훨씬 입체적으로 만든다.

#### 4.2.1. 현재 흐름을 그려야 병목과 중복이 보인다

업무 프로세스를 시각화하면 말로는 막연했던 문제가 갑자기 구조로 드러난다. 어디서 지연이 생기는지, 어떤 승인 단계가 중복되는지, 누가 같은 내용을 반복 입력하는지, 어떤 단계가 없어도 되는지가 눈에 보이기 시작한다.

교안의 사례처럼 배송기사 배정 단계의 지연, 중복 검토, 긴 상담 대기, 과도한 수작업은 코드만 보고는 잘 드러나지 않는다. 흐름 전체를 그려 봐야 보이는 문제들이다.

#### 4.2.2. `To-Be`는 예쁜 미래상이 아니라 소프트웨어가 지원해야 할 목표 흐름이다

`To-Be` 프로세스는 가끔 이상적인 그림처럼만 받아들여지는데, 교안을 따라가 보니 훨씬 실용적인 의미가 있었다. 결국 `To-Be`는 소프트웨어가 실제로 지원해야 할 업무 흐름이다. 이후의 화면, 기능, API, 권한 구조, 데이터 저장 방식은 모두 이 목표 흐름을 구현하기 위해 세분화된다.

프론트엔드 입장에서도 이 점이 중요하다. 웹페이지 하나는 독립적으로 존재하는 게 아니라 전체 프로세스 속 한 단계일 때가 많다. 상품을 보고, 장바구니에 넣고, 결제하고, 배송을 추적하는 각 화면도 결국 `To-Be` 프로세스를 눈앞의 인터페이스로 풀어낸 결과다. 그래서 `To-Be`를 제대로 이해하지 못하면 화면은 예뻐 보여도 흐름은 어색해지기 쉽다.

## 5. 이번 단원을 지나며 더 강해진 생각은 "좋은 구현은 좋은 요구분석 뒤에서 나온다"는 것이다

이번 3주차 `요구분석` 파트는 코딩 전 단계의 문서 절차를 설명하는 과목처럼 보일 수 있다. 하지만 실제로는 그보다 훨씬 중요했다. 무엇을 만들어야 하는지, 왜 만들어야 하는지, 어떤 수준으로 잘 만들어져야 하는지, 현재 프로세스에서 무엇을 바꿔야 하는지를 초반에 정리하지 않으면, 뒤에서 아무리 열심히 구현해도 흔들릴 수밖에 없다는 사실을 아주 선명하게 보여 줬기 때문이다.

현업 프론트엔드 개발자로서도 이번 단원은 꽤 직접적인 공부가 됐다. 화면은 요구의 결과물이기 때문에, 요구가 모호하면 UI도 모호해진다. 성능 기준이 비어 있으면 체감 품질이 흔들리고, 예외 규칙이 빠져 있으면 인터랙션이 어색해지고, 프로세스가 정리되지 않으면 화면 전환 자체가 납득되지 않는다. 결국 좋은 화면은 좋은 감각의 문제가 아니라, **탄탄한 요구분석 위에서만 오래 유지될 수 있는 결과물**이라는 생각이 이번 주차를 지나며 더 강하게 남았다.
