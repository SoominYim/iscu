# [데이터베이스] 데이터베이스 학습 (2) - 프론트엔드도 DBMS를 알아야 할까?

프론트엔드 개발을 하다 보면 가끔 이런 생각을 하게 된다.

"DB는 백엔드가 알아서 하는 거 아닌가?"

실제로 테이블을 설계하고 인덱스를 잡고 트랜잭션을 튜닝하는 건 보통 백엔드나 데이터 엔지니어의 역할에 더 가깝다. 그래서 처음에는 데이터베이스를 조금 멀리 있는 세계처럼 느끼기 쉽다. 그런데 막상 서비스를 만들다 보면 프론트엔드도 데이터 저장 방식의 영향을 아주 직접적으로 받는다. 목록 화면이 왜 이렇게 느린지, 왜 어떤 값은 바로 반영되지 않는지, 왜 검색 결과가 중복되거나 누락되는지, 왜 응답 구조가 자꾸 바뀌는지 따라가다 보면 결국 데이터 관리 방식에 닿게 된다.

이번 2주차 데이터베이스는 바로 그 출발점인 `DBMS`를 다뤘다. 파일 시스템 방식의 한계, DBMS의 개념과 특징, 기능과 장단점, 그리고 계층형에서 관계형, NoSQL, NewSQL로 이어지는 발전 흐름까지. 정리하고 나니 데이터베이스는 단순히 "데이터 넣는 곳"이 아니라, **서비스가 데이터를 다루는 질서를 만드는 시스템**에 더 가깝게 느껴졌다.

## 이번 주차를 읽기 전에 먼저 던져볼 질문

이번 2주차는 다음 질문을 계속 머리에 두고 읽으면 이해가 더 잘 된다.

- 왜 파일로 저장하는 것만으로는 부족할까?
- DBMS는 정확히 어떤 문제를 해결해줄까?
- `CREATE`, `SELECT`, `UPDATE` 같은 기능은 왜 나뉘어 있을까?
- 왜 관계형 DB와 NoSQL이 공존할까?

이 질문에 답이 생기면 교안의 개념들이 그냥 용어 암기가 아니라, 실제 시스템 설계의 판단 기준으로 연결된다.

## 왜 파일 시스템만으로는 부족할까

처음에는 누구나 이렇게 생각하기 쉽다.

"작은 프로그램이면 그냥 파일로 저장하면 되는 거 아닌가?"

실제로 아주 작은 개인 프로젝트나 일회성 스크립트라면 파일 저장만으로도 충분할 수 있다. 그런데 교안에서는 파일 시스템 방식의 문제를 꽤 명확하게 짚고 있었다.

### 1. 중복 저장

서로 다른 프로그램이 같은 데이터를 각자 따로 저장하면 중복이 생긴다. 교안 예시처럼 인사관리 프로그램과 회계관리 프로그램이 각자 직원 데이터를 따로 갖고 있으면, 이름이나 연락처 같은 정보가 여러 파일에 반복 저장될 수 있다.

문제는 여기서 끝나지 않는다.

- 저장 공간이 낭비된다.
- 한쪽만 수정되면 다른 쪽과 값이 달라진다.
- 어느 파일이 최신인지 판단하기 어려워진다.

이건 프론트엔드에서도 꽤 익숙한 문제다. 전역 상태, 서버 상태, 캐시 상태가 여기저기 중복되기 시작하면 결국 "어디가 진짜 값이지?"라는 문제가 생긴다. 데이터 중복은 저장 계층만의 문제가 아니라, 상태 관리 전반에서 반복해서 나타나는 구조적 문제다.

### 2. 응용 프로그램의 데이터 파일 종속성

파일 구조가 바뀌면 그 파일을 읽는 프로그램도 같이 바뀌어야 한다. 즉 데이터 형식과 응용 프로그램 코드가 너무 강하게 묶여 있는 상태다.

예를 들어 인사데이터 파일에 `PLACE` 컬럼 하나를 추가했더니, 그 파일을 읽는 프로그램 전부를 수정해야 하는 상황이 생길 수 있다. 작은 변경인데도 파급 범위가 커진다.

이건 프론트엔드가 API 응답 구조에 너무 강하게 의존할 때 벌어지는 상황과 닮아 있다. 필드 하나 추가되거나 이름이 바뀌었을 뿐인데 화면이 줄줄이 깨진다면, 결국 데이터 구조와 프로그램이 너무 단단하게 묶여 있다는 뜻이다.

### 3. 병행 처리의 어려움

여러 사용자가 동시에 같은 데이터에 접근하면 충돌이나 무결성 문제가 생긴다. 교안에서도 이 부분을 파일 시스템 방식의 중요한 한계로 설명하고 있었다.

예를 들어 같은 상품 재고를 두 사용자가 거의 동시에 구매하는 상황을 떠올려보면 이해가 쉽다.

- A가 재고 1개를 확인한다.
- B도 거의 동시에 재고 1개를 확인한다.
- 둘 다 구매를 완료한다.

결과적으로 재고는 음수가 되거나, 시스템 기록은 꼬일 수 있다. 파일 저장만으로 이런 충돌을 안정적으로 해결하는 건 생각보다 어렵다. 결국 데이터 관리에는 저장뿐 아니라 **동시 접근을 제어하는 능력**이 필요하다.

## DBMS는 정확히 어떤 역할을 할까

교안에서는 DBMS를 사용자와 데이터베이스 사이에서 데이터베이스를 관리하는 소프트웨어라고 설명한다. 이 정의를 조금 쉽게 풀어보면, DBMS는 단순한 저장소가 아니라 **데이터를 안전하고 일관되게 읽고 쓰게 해주는 관리자**다.

즉 DBMS는 다음을 도와준다.

- 데이터를 한곳에서 통합 관리한다.
- 여러 프로그램이 같은 데이터를 공유할 수 있게 한다.
- 데이터 중복과 불일치를 줄인다.
- 동시 접근 상황에서도 무결성을 유지한다.
- 권한과 보안을 관리한다.
- 필요한 형태로 데이터를 질의할 수 있게 한다.

이 설명을 듣고 나니 DBMS는 데이터 자체보다 "데이터를 다루는 방식"을 관리하는 시스템에 더 가깝게 느껴졌다.

## DBMS의 특징을 보면 왜 필요한지 더 명확해진다

교안에서는 DBMS의 특징을 데이터 통합, 독립성, 일관성, 보안성, 경제성, 무결성 같은 키워드로 정리하고 있었다. 하나씩 보면 실무 감각으로도 꽤 이해가 잘 된다.

### 데이터 통합

데이터를 중앙에서 통합 관리하면 중복이 줄어든다. 중복이 줄어들면 저장 낭비도 줄고, 값이 서로 다르게 유지될 가능성도 줄어든다.

프론트엔드 입장에서도 이건 중요하다. 같은 사용자 정보가 A API와 B API에서 서로 다르게 내려오면 UI 로직이 순식간에 지저분해진다. 데이터가 통합되어 있을수록 화면은 단순해진다.

### 독립성

DBMS의 중요한 장점 중 하나는 데이터 구조가 바뀌더라도 응용 프로그램 전체를 다 뜯어고치지 않도록 완충 역할을 한다는 점이다.

교안에서도 데이터베이스 구조가 바뀌어도 응용 프로그램 수정을 최소화할 수 있다고 설명하고 있었는데, 이 부분이 특히 실무적이었다. 스키마는 영원히 고정되지 않는다. 필드가 추가되고, 관계가 바뀌고, 요구사항이 수정된다. 이때 독립성이 확보되어 있지 않으면 작은 구조 변경이 곧 장애가 된다.

### 일관성과 무결성

같은 데이터는 어디서 보더라도 같은 의미를 가져야 한다. 또 잘못된 값이 들어가지 않도록 규칙을 유지해야 한다. 이게 일관성과 무결성이다.

예를 들어 학점은 `0~4.5` 범위를 벗어나면 안 되고, 재고는 음수가 되면 안 되고, 존재하지 않는 부서코드를 참조하면 안 된다. 이런 규칙이 지켜져야 시스템이 믿을 만해진다.

### 보안성

모든 사용자가 모든 데이터를 마음대로 볼 수 있거나 수정할 수 있으면 서비스는 바로 무너진다. DBMS는 권한 관리와 접근 제어를 지원한다.

프론트엔드 관점에서는 이게 UI 설계와도 연결된다. 어떤 사용자에게 어떤 버튼을 보여줄지, 어떤 정보는 읽기만 가능하고 어떤 정보는 수정 가능하게 할지, 관리자 화면을 어떻게 분리할지 같은 판단은 결국 데이터 권한 구조와 이어진다.

## DBMS의 기능은 결국 정의하고, 조작하고, 통제하는 일이다

교안에서는 DBMS 기능을 크게 세 가지로 볼 수 있었다.

### 1. 정의 기능

데이터 구조를 정의, 변경, 삭제하는 기능이다.

- `CREATE`
- `ALTER`
- `DROP`

즉 어떤 테이블이 있고, 어떤 컬럼을 가지고, 어떤 제약조건을 가지는지를 정하는 역할이다. 쉽게 말하면 데이터 저장의 뼈대를 만드는 단계다.

### 2. 조작 기능

사용자와 데이터베이스 사이의 인터페이스 역할을 하며 실제 데이터를 다루는 기능이다.

- `INSERT`
- `DELETE`
- `UPDATE`
- `SELECT`

이 부분은 프론트엔드와도 굉장히 가깝다. 결국 대부분의 관리자 화면, 목록 화면, 검색 화면, 편집 화면은 이 조작 기능의 인터페이스다. 사용자는 버튼을 누르고 폼을 입력하지만, 그 뒤에서는 생성, 조회, 수정, 삭제가 일어난다.

### 3. 제어 기능

교안 후반에서는 제어 기능도 따로 다루고 있었다.

- `GRANT`
- `REVOKE`
- `COMMIT`
- `ROLLBACK`

이 기능들은 권한 관리와 트랜잭션 제어에 가깝다. 즉 누가 무엇을 할 수 있는지, 그리고 작업을 확정할지 취소할지를 다룬다. 이런 기능이 있다는 것 자체가 DBMS가 단순 보관함이 아니라 관리 시스템이라는 걸 보여준다.

## 질의(Query)를 이해하면 서비스 화면이 다르게 보인다

이번 주차에서 꽤 재밌었던 부분은 질의 예시였다.

- "신규고용 정책을 제안한 부서명?"
- "총무과에서 제안한 정책번호를 999로 변경하세요."
- "DB를 수강한 학생 이름은?"

이 예시들을 보면서 느낀 건, 사용자가 머릿속에 떠올리는 자연어 질문과 데이터베이스가 실행하는 질의는 결국 같은 목적을 가진다는 점이다. 표현만 다를 뿐이다.

프론트엔드 개발자에게 이 감각은 꽤 중요하다. 왜냐하면 검색 UI, 필터 UI, 관리자 테이블, 대시보드 위젯, 자동완성 입력창은 전부 결국 데이터 질의를 사람이 쓰기 쉽게 바꿔놓은 인터페이스이기 때문이다.

즉 좋은 화면을 만든다는 건 예쁜 레이아웃만의 문제가 아니라, 사용자의 질문을 얼마나 자연스럽게 질의로 번역하게 돕는지의 문제이기도 하다.

## DBMS의 장점만 보면 안 되는 이유

교안에서는 DBMS의 장단점을 모두 다뤘다. 이 부분이 꽤 현실적으로 느껴졌다. 좋은 기술이라는 말과 항상 써야 한다는 말은 다르기 때문이다.

### 장점

교안에서 정리한 DBMS의 장점은 다음과 같은 방향으로 이해할 수 있었다.

- 데이터 중복 최소화
- 독립성 확보
- 동시 공유 가능
- 보안 향상
- 무결성 유지
- 표준화 가능
- 응용 프로그램 개발 편의 향상

즉 규모가 커질수록, 사용자 수가 많을수록, 데이터가 자주 공유될수록 DBMS의 가치가 커진다.

### 단점

하지만 DBMS는 만능 도구가 아니다.

- 구축 비용이 든다.
- 시스템이 복잡해진다.
- 전문적인 관리가 필요하다.
- 소규모 자동화 영역에서는 오히려 과할 수 있다.

교안에서도 항공기 예약 시스템처럼 동시성과 무결성이 중요한 경우 DBMS가 꼭 필요하다고 설명하는 반면, 간단한 개인 프로젝트나 정적 웹사이트, 매우 제한된 사용자 환경에서는 필요성이 낮을 수 있다고 정리하고 있었다.

이 판단은 프론트엔드 실무에서도 익숙하다. 작은 화면 하나 만드는데 거대한 상태 관리 구조를 얹는 게 항상 정답이 아닌 것처럼, 데이터 저장도 규모와 요구사항에 맞춰 선택해야 한다.

## DBMS의 발전 과정을 보면 지금 기술 선택도 조금 더 이해된다

후반부에서 다룬 DBMS 유형과 발전 과정은 교과서적인 내용처럼 보이지만, 현재 기술 스택을 이해하는 데 꽤 도움이 된다.

### 계층형 DBMS

트리 구조로 데이터를 표현하는 방식이다. 부모-자식 관계가 명확한 데이터에는 적합하지만, 관계가 복잡해지면 유연성이 떨어진다.

### 네트워크형 DBMS

계층형보다 더 복잡한 관계를 표현할 수 있지만, 구조가 복잡하고 다루기 어렵다. 다대다 관계를 표현할 수 있는 장점은 있지만 그만큼 설계와 관리가 까다롭다.

### 관계형 DBMS

가장 익숙한 형태다. 표 형태의 데이터, SQL 질의, 관계 중심 구조를 사용한다. 교안에서도 Oracle, MySQL, PostgreSQL, SQL Server 같은 예를 들고 있었다.

현대 웹 서비스의 상당수는 여전히 관계형 데이터베이스를 핵심으로 사용한다. 이유는 명확하다.

- 데이터 구조가 비교적 명확하다.
- 질의 언어가 강력하다.
- 무결성과 트랜잭션 관리가 안정적이다.

프론트엔드 입장에서도 사용자, 상품, 주문, 리뷰, 결제 같은 엔티티가 관계를 맺는 구조는 너무 익숙하다. 실제로 화면은 관계형 데이터 모델을 여러 방식으로 보여주는 경우가 많다.

### 객체지향 DBMS

객체지향 개념을 데이터 저장 구조에 반영하려는 흐름이다. 클래스, 상속, 캡슐화 같은 개념과 연결된다. 지금 실무에서 주류라고 보긴 어렵지만, 데이터와 객체 모델의 거리를 좁히려는 시도라는 점에서는 흥미롭다.

### NoSQL

교안에서는 NoSQL을 문서 기반, 키-값 기반, 컬럼 기반, 그래프 기반 데이터베이스로 나눠 설명하고 있었다. 관계형 데이터베이스보다 유연한 구조를 제공하고, 대규모 분산 처리에 강한 특성이 있다.

특히 JSON과 비슷한 문서 기반 구조는 프론트엔드에게도 낯설지 않다. 우리가 API로 자주 받는 응답도 대부분 객체와 배열 형태의 JSON이기 때문이다.

### NewSQL

NewSQL은 관계형 DBMS의 SQL과 무결성 장점을 유지하면서도, 대규모 분산 환경의 확장성을 확보하려는 시도다. 교안에서는 Google Spanner, CockroachDB 같은 예시를 언급하고 있었다.

이 흐름을 보면 관계형과 NoSQL이 단순한 경쟁 관계라기보다, 각자의 장단점을 가진 도구라는 점이 더 분명해진다.

## 프론트엔드 개발자에게 DBMS 이해가 왜 필요할까

이번 2주차를 정리하면서 가장 크게 든 생각은 이거였다.

**프론트엔드가 DB를 직접 다루지 않는다고 해서, DBMS를 몰라도 되는 건 아니다.**

이유는 간단하다. 화면은 결국 데이터 위에 세워지기 때문이다.

- 검색 UI는 질의를 전제로 한다.
- 관리자 페이지는 생성/수정/삭제 흐름을 전제로 한다.
- 실시간 반영 여부는 동시성 처리와 연결된다.
- 응답 구조는 데이터 모델의 영향을 받는다.
- 권한 UI는 보안 구조와 연결된다.

즉 화면 개발은 데이터 계층과 완전히 분리된 세계가 아니다. 오히려 사용자에게 가장 가까운 층에서 데이터 구조의 결과를 드러내는 역할에 가깝다.

## 2주차를 정리하며

이번 2주차 데이터베이스를 통해 정리된 건 DBMS를 보는 시선이었다.

DBMS는 단순히 데이터를 넣어두는 창고가 아니라, 중복을 줄이고, 일관성을 지키고, 동시 접근을 관리하고, 보안을 확보하고, 필요한 형태로 질의할 수 있게 해주는 관리 시스템이다. 그리고 그 위에서 정의 기능, 조작 기능, 제어 기능이 돌아간다.

특히 파일 시스템과 비교하면서 보니 왜 DBMS가 필요한지가 훨씬 또렷해졌다. 저장 그 자체보다 중요한 건 **변경과 공유와 동시 접근을 어떻게 감당하느냐**였다.

프론트엔드 개발자로서도 이 내용은 충분히 실무적이었다. 결국 내가 만드는 화면은 데이터의 결과를 보여주는 최전선이고, 데이터가 어떤 구조로 저장되고 어떤 방식으로 조회되는지 이해할수록 UI도 더 현실적으로 설계할 수 있다.

예전에는 데이터베이스를 조금 멀리 있는 영역처럼 느꼈는데, 이번 주차를 정리하고 나니 생각이 꽤 달라졌다. 데이터베이스는 백엔드만의 세계가 아니라, 서비스의 안정감과 속도와 일관성을 만드는 가장 바닥의 기반에 가까웠다. 그리고 그 기반을 이해할수록, 화면을 만드는 판단도 훨씬 선명해진다는 걸 이번 주차를 통해 다시 느꼈다.
