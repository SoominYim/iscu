# [객체지향프로그래밍] 객체지향프로그래밍 학습 (2) - 자바는 왜 데이터 타입을 이렇게 깐깐하게 다룰까?

자바를 다시 볼 때마다 드는 생각이 있다.

"왜 이렇게 하나하나 다 선언하게 하지?"

프론트엔드 개발자로 오래 일하다 보면 자바스크립트나 타입스크립트 쪽 감각에 익숙해진다. 타입스크립트도 타입을 중요하게 보지만, 런타임 자체는 비교적 유연하고 실험 속도도 빠른 편이다. 반면 자바는 변수를 선언할 때부터 자료형을 분명히 해야 하고, 출력 방식도 나뉘어 있고, 입력도 명시적으로 받아야 하고, 자료형 변환도 함부로 넘어가지 않는다.

이번 2주차 객체지향프로그래밍 교안의 주제는 `JAVA 데이터 처리`였다. `System.out.print`, `System.out.println`, `System.out.printf` 같은 출력 방식부터 `Scanner`를 통한 입력, 변수의 선언과 명명 규칙, 기본형과 참조형 데이터 타입, 초기화, 리터럴, 자료형 변환까지. 겉보기에는 문법 수업처럼 보이지만, 실제로는 자바가 데이터를 얼마나 엄격하게 다루는 언어인지 보여주는 흐름이었다.

정리하고 나니 이번 주차는 단순한 문법 암기보다 "자바는 왜 이렇게까지 타입과 데이터 표현을 분명하게 요구할까?"라는 질문에 답하는 시간에 더 가까웠다.

## 이번 주차를 이해할 때 붙잡고 있으면 좋은 질문

이번 2주차를 보면서 계속 머리에 두었던 질문은 다음 네 가지였다.

- 자바는 왜 출력 방식조차 나눠서 제공할까?
- 입력을 받을 때 왜 타입별 메서드를 따로 쓸까?
- 기본형과 참조형은 왜 굳이 나눠서 설명할까?
- 자료형 변환은 왜 자동으로 되지 않고, 어떤 경우엔 강제 캐스팅을 요구할까?

이 질문에 답이 생기면, 자바의 "깐깐함"이 귀찮은 제약이라기보다 시스템 안정성을 위한 장치처럼 보이기 시작한다.

## 출력부터 나눠서 가르치는 이유

교안 초반에서는 데이터 출력 방식부터 다뤘다.

- `System.out.print()`
- `System.out.println()`
- `System.out.printf()`

처음 보면 정말 사소한 차이처럼 느껴진다. 그런데 이 세 가지를 구분해서 보는 순간 자바가 "출력도 데이터 표현 방식의 일부"라고 생각하는 언어라는 게 보인다.

### print와 println

`print()`는 줄바꿈 없이 출력하고, `println()`은 출력 뒤에 줄바꿈을 해준다. 얼핏 보면 정말 단순한 차이다. 하지만 실제로는 화면에 정보가 어떻게 읽히는지를 제어하는 가장 기본적인 방식이다.

예를 들어 로그를 찍거나 콘솔 출력을 정리할 때 줄바꿈 하나 차이로 가독성이 크게 달라진다. 이건 프론트엔드에서 `console.log()`를 무심코 찍다가도 결국 출력 형식을 정리하게 되는 경험과 닮아 있다.

### printf와 형식 지정자

`printf()`는 여기서 한 단계 더 나간다. 단순히 값을 찍는 게 아니라, **어떤 형식으로 표현할지까지 지정해서 출력**한다.

교안에서 다룬 예시는 다음과 같은 흐름이었다.

- `%s`: 문자열
- `%d`: 정수
- `%f`: 실수
- `%c`: 문자

이걸 보면서 다시 느낀 건 자바는 "이 값이 무엇인지"를 출력 순간에도 놓치지 않는다는 점이다. 문자열인지 숫자인지, 소수점이 있는 값인지 문자 하나인지에 따라 표현 방식이 달라진다.

실무에서도 이 감각은 중요하다. 예를 들어 관리자 화면에서 숫자를 천 단위 콤마로 보여줄지, 퍼센트를 소수 둘째 자리까지 보여줄지, 날짜를 어떤 포맷으로 보여줄지 정하는 일은 결국 값의 의미를 먼저 이해해야 가능한 작업이다.

## 이스케이프 시퀀스는 사소하지만 정말 자주 쓴다

교안 중간에는 이스케이프 시퀀스도 나왔다.

- `\n`: 줄바꿈
- `\t`: 탭
- `\\`: 백슬래시
- `\"`: 큰따옴표
- `\'`: 작은따옴표

처음 배울 땐 되게 사소해 보이는데, 문자열 출력과 포맷팅에서는 계속 등장한다. 특히 사용자에게 보여주는 메시지, 로그 문자열, JSON 문자열, 특수문자 출력 같은 부분에서는 기본 중의 기본이다.

프론트엔드에서도 템플릿 문자열이나 HTML 엔티티, JSON escape 처리를 계속 만나는 걸 떠올리면, 결국 문자열은 "그냥 글자"가 아니라 규칙에 따라 표현되는 데이터라는 걸 다시 느끼게 된다.

## 입력을 받는다는 건 데이터를 믿지 않는다는 뜻이기도 하다

이번 주차에서 꽤 실무적으로 다가온 부분은 `Scanner` 클래스를 이용한 입력 파트였다.

- `nextBoolean()`
- `nextByte()`
- `nextShort()`
- `nextInt()`
- `nextLong()`
- `nextFloat()`
- `nextDouble()`
- `nextLine()`

교안은 이 메서드들을 단순 표로 정리하고 있지만, 읽다 보면 꽤 중요한 메시지가 보인다.

**입력은 언제나 타입과 함께 받아야 한다.**

즉 사용자가 입력한 값은 그냥 문자열 덩어리가 아니라, 어떤 타입으로 해석할 것인지가 먼저 정해져야 한다. 이건 생각보다 중요한 태도다.

왜냐하면 사용자 입력은 늘 예상 밖이기 때문이다.

- 숫자 칸에 문자를 넣을 수도 있고
- 공백과 줄바꿈 때문에 읽기 방식이 달라질 수도 있고
- 값은 숫자처럼 보여도 실제로는 문자열일 수 있다

프론트엔드에서 폼 검증을 할 때도 똑같다. 결국 입력은 받는 것보다 **어떻게 검증하고 어떤 타입으로 해석할 것인가**가 더 중요하다.

## 변수는 저장공간이자 약속이다

중반부에서는 변수 선언과 명명 규칙이 이어진다. 처음에는 너무 당연한 이야기처럼 보인다.

- 변수는 데이터를 저장할 수 있는 메모리 공간이다.
- 선언할 때 자료형과 이름을 함께 적는다.
- 식별자 규칙을 지켜야 한다.

그런데 자바에서는 이게 단순 문법 설명으로 끝나지 않는다. 변수를 선언하는 순간 "이 변수에는 이런 종류의 데이터만 들어온다"는 약속도 함께 생긴다.

예를 들어:

```java
int num;
double score;
char grade;
```

이렇게 선언하면 각 변수는 단순한 이름표가 아니라, 데이터의 성격을 명확히 규정하는 역할을 한다.

교안에서 식별자 규칙을 별도로 강조한 것도 이해가 갔다. 이름은 단순 취향이 아니라, 코드를 읽는 사람에게 데이터의 역할을 설명하는 첫 번째 문장에 가깝기 때문이다.

프론트엔드에서 타입스크립트를 쓰면서 인터페이스 이름, 상태 변수 이름, props 이름에 신경 쓰는 이유도 결국 같다. 코드가 길어질수록 명확한 이름이 곧 가독성이 된다.

## 자바의 기본형 데이터 타입은 왜 이렇게 세세할까

이번 주차의 핵심은 역시 데이터 타입이었다. 교안에서는 `boolean`, `char`, `byte`, `short`, `int`, `long`, `float`, `double`을 표와 함께 설명하며 각 타입의 저장 크기와 표현 범위를 정리하고 있었다.

이 부분을 보고 가장 크게 느낀 건, 자바는 "값"보다 "값을 어떻게 저장할 것인가"를 먼저 생각하게 만드는 언어라는 점이었다.

### boolean

`true`와 `false`를 저장하는 타입이다. 단순해 보여도 조건 분기와 상태 표현의 핵심이다.

프론트엔드에서도 `isLoading`, `isOpen`, `isValid`, `hasError` 같은 값은 대부분 boolean이다. 결국 프로그램의 분기는 상당 부분 이 타입 위에서 움직인다.

### char

문자 하나를 저장하는 타입이다. 교안에서는 유니코드와 연결해서 설명하고 있었는데, 여기서 중요한 건 문자가 감성적인 글자가 아니라 **코드 값으로 저장되는 데이터**라는 점이다.

즉 `char`는 "글자"를 저장하는 게 아니라, 해당 문자를 표현하는 코드 값을 저장한다고 보는 편이 더 정확하다.

### byte, short, int, long

정수형 타입이 여러 개 존재하는 이유는 단순하다. 표현 가능한 범위와 메모리 크기가 다르기 때문이다.

- `byte`: 1byte
- `short`: 2byte
- `int`: 4byte
- `long`: 8byte

교안에서는 각 타입의 표현 범위를 함께 보여주고 있었는데, 이걸 보니 왜 타입을 여러 개 나눠 놓았는지가 더 분명해졌다. 결국 데이터는 항상 메모리 공간을 차지하고, 그 공간 안에서 표현 가능한 범위가 정해져 있다.

### float, double

실수형 타입이다.

- `float`: 4byte
- `double`: 8byte

실수는 정수보다 훨씬 까다롭다. 소수점 아래까지 표현해야 하고, 그 과정에서 부동소수점 방식이 사용되기 때문이다. 그래서 자바는 아예 실수형 타입을 따로 두고 저장 방식까지 분명하게 구분한다.

이건 프론트엔드에서도 너무 익숙하다. `0.1 + 0.2` 같은 계산이 깔끔하게 떨어지지 않는 문제는 결국 부동소수점 표현 방식과 연결된다. 언어가 달라도 본질은 같다.

## 메모리 관점으로 보니까 타입이 훨씬 현실적으로 다가왔다

교안에서는 실제 메모리에 저장되는 단위인 비트와 바이트를 다시 꺼내면서 데이터 타입을 설명하고 있었다. 이 부분이 좋았던 이유는 문법을 암기하는 느낌에서 한 단계 더 내려가게 만들기 때문이다.

예를 들어:

- `byte`는 1바이트이므로 표현 범위가 작다
- `int`는 4바이트이므로 더 넓은 범위를 갖는다
- `double`은 8바이트라 더 큰 정밀도를 가진다

이걸 보면 자료형은 단순한 이름표가 아니라, 실제 메모리 설계와 맞닿아 있는 선택이라는 게 보인다.

프론트엔드는 보통 메모리 단위를 직접 의식하지 않고 작업하는 경우가 많지만, 성능 최적화나 저수준 API, 대용량 데이터 처리, 그래픽스, 바이너리 포맷 쪽으로 가면 결국 다시 이 감각이 필요해진다.

## 기본형과 참조형을 나누는 이유

후반부에서는 참조형 데이터 타입도 나왔다. 대표적인 예가 `String`이다. 여기서 핵심은 자바가 데이터를 크게 두 부류로 본다는 점이다.

- 기본형: 값을 직접 저장
- 참조형: 객체를 가리키는 참조를 저장

이 차이는 생각보다 중요하다. 왜냐하면 "값을 다루는 것"과 "객체를 다루는 것"은 전혀 다른 문제이기 때문이다.

프론트엔드에서도 비슷하다.

- 숫자나 문자열 같은 원시값은 비교가 단순하다
- 배열과 객체는 참조 공유 문제가 생긴다
- 같은 내용처럼 보여도 실제로는 다른 객체일 수 있다

자바는 이 차이를 굉장히 일찍, 그리고 분명하게 가르친다. 나중에 객체지향 개념을 배울 때 헷갈리지 않으려면 이 구분이 반드시 필요하기 때문이다.

## 초기화는 왜 강조할까

교안에서는 변수 초기화와 기본값도 따로 설명하고 있었다. 처음 보면 너무 당연한 이야기처럼 보이는데, 실무에서는 오히려 여기서 자주 흔들린다.

- 변수에 값을 넣기 전에 사용하려고 한다
- 기본값이 있을 거라고 착각한다
- `null` 상태를 놓치고 사용한다

교안의 표를 보면 기본형과 참조형의 기본값이 어떻게 다른지도 정리돼 있다. 이걸 보면 초기화는 단순한 문법 절차가 아니라, **이 변수가 지금 유효한 상태인가**를 보장하는 과정처럼 느껴진다.

프론트엔드에서도 `undefined`, `null`, 빈 문자열, 숫자 0을 구분하지 못하면 바로 버그가 난다. 결국 초기화는 프로그램이 정상 상태로 출발하기 위한 최소 조건이다.

## 리터럴은 값의 모습이자 의도다

이번 주차에서는 리터럴도 꽤 비중 있게 다뤘다.

- 정수 리터럴
- 실수 리터럴
- 문자 리터럴
- 문자열 리터럴
- 논리 리터럴
- `null`

이걸 왜 따로 설명할까 생각해봤는데, 리터럴은 값의 모양과 의도를 코드에 직접 드러내기 때문이다.

예를 들어:

```java
10        // 정수 리터럴
10.0      // 실수 리터럴
'A'       // 문자 리터럴
"JAVA"    // 문자열 리터럴
true      // 논리 리터럴
10000000000L // long 리터럴
3.14f     // float 리터럴
```

특히 `L`, `f` 같은 접미사를 붙이는 부분은 자바가 "이 값이 어떤 타입인지 정확히 알려달라"고 요구하는 대표적인 장면처럼 보였다.

## 자료형 변환은 편의를 위한 기능이 아니라 안전장치다

마지막 파트는 데이터 자료형 변환이었다. 교안에서는 작은 범위에서 큰 범위로 가는 자동 변환과, 큰 범위에서 작은 범위로 바꾸는 강제 변환을 비교하고 있었다.

### 자동 형 변환

작은 범위를 가진 타입이 더 큰 범위의 타입으로 이동할 때는 비교적 안전하다.

예를 들어:

```java
byte b = 10;
int n = b;
double d = n;
```

이 과정은 정보 손실 가능성이 낮기 때문에 자동으로 허용된다.

### 강제 형 변환

반대로 큰 범위 타입을 작은 범위 타입으로 바꿀 때는 위험이 있다.

```java
int n = 130;
byte b = (byte)n;
```

이 경우 표현 범위를 넘어가면 값이 달라질 수 있다. 그래서 자바는 개발자에게 명시적으로 캐스팅하라고 요구한다.

이 부분을 보면서 느낀 건 자료형 변환은 편한 기능이 아니라 **데이터 손실에 대한 경고 체계**에 가깝다는 점이었다.

프론트엔드에서도 이 감각은 되게 중요하다.

- 문자열 `"10"`을 숫자 `10`으로 바꿀 것인가
- 소수점을 정수로 바꿀 때 반올림할 것인가 버릴 것인가
- 서버 응답을 화면용 포맷으로 바꿀 때 값이 왜곡되지 않는가

즉 타입 변환은 단순한 문법 문제가 아니라, 데이터 해석과 책임의 문제다.

## 자바의 엄격함은 생각보다 합리적이다

이번 주차를 정리하면서 계속 든 생각은 자바가 괜히 답답한 언어가 아니라는 점이었다. 물론 빠르게 화면을 붙이고 실험하는 입장에서는 분명 번거롭게 느껴질 수 있다. 하지만 큰 시스템을 오래 유지해야 하고, 여러 명이 함께 개발하고, 데이터가 명확해야 하는 환경에서는 이 엄격함이 오히려 장점이 될 수 있다.

어떤 값인지, 얼마나 저장할 수 있는지, 어떤 방식으로 출력할지, 어떤 타입으로 입력받을지, 어떻게 변환할지를 처음부터 분명히 해두는 태도는 결국 나중의 혼란을 줄여준다.

타입스크립트를 적극적으로 쓸 때 느끼는 감각과도 닮아 있다. 처음엔 귀찮아도 프로젝트가 커질수록 타입 정보가 오히려 나를 도와준다.

## 2주차를 정리하며

이번 2주차 객체지향프로그래밍은 겉으로는 문법 수업처럼 보였지만, 실제로는 자바가 데이터를 바라보는 태도를 배우는 시간에 가까웠다.

출력 방식의 차이, `Scanner`를 이용한 입력, 변수 선언, 식별자 규칙, 기본형과 참조형, 초기화, 리터럴, 자료형 변환까지 전부 하나의 메시지로 이어졌다.

**데이터를 모호하게 다루지 말 것.**

프론트엔드 개발자로서도 이 메시지는 꽤 크게 다가왔다. 화면은 유연하게 보여도, 그 아래에서 다루는 데이터까지 흐릿하면 결국 버그와 오해가 쌓인다. 자바는 그걸 아주 정직하게 드러내는 언어였다.

예전에는 자바의 타입 시스템이 조금 답답하게만 느껴졌는데, 이번 주차를 정리하고 나니 생각이 꽤 달라졌다. 이 엄격함은 제약이기도 하지만, 동시에 복잡한 프로그램을 안정적으로 다루기 위한 최소한의 안전장치이기도 했다. 그래서 이번 주차는 단순한 기초 문법이 아니라, 앞으로 더 큰 시스템을 읽고 쓰기 위해 필요한 태도를 익히는 시간이었다고 느껴진다.
