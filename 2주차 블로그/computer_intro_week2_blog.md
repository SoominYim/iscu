# [컴퓨터개론] 컴퓨터개론 학습 (2) - 2진수와 16진수는 왜 아직도 중요할까?

프론트엔드 개발을 하다 보면 은근히 숫자와 기호에 자주 부딪힌다. 이미지 용량을 줄일 때는 `KB`, `MB`를 보고, 네트워크 속도를 이야기할 때는 `Mbps`를 보고, CSS에서 색상을 다룰 때는 `#FF5733` 같은 16진수 코드를 본다. 평소에는 너무 익숙해서 그냥 지나가는데, 막상 **컴퓨터가 왜 이런 방식으로 정보를 표현하는지**를 설명하려고 하면 순간 머뭇거리게 된다.

이번 2주차 컴퓨터개론은 바로 그 지점을 정리하는 시간이었다. 디지털 정보 표현, 컴퓨터에서 쓰는 단위, 2진수와 16진수 변환, 정수와 실수의 저장 방식, 문자 코드, 논리 연산과 논리 게이트까지. 얼핏 보면 전부 "너무 기초 아닌가?" 싶은 주제들인데, 이상하게도 실무에 가까워질수록 다시 자주 만나게 되는 개념들이다.

특히 현업에서 프론트엔드 개발을 하다 보면 이 내용이 더 와닿는다. 브라우저가 다루는 HTML, CSS, JavaScript도 결국은 디지털 데이터고, 우리가 성능을 개선하고 색상을 지정하고 파일 크기를 줄이고 네트워크 병목을 파악하는 일도 전부 이 표현 방식 위에서 벌어진다. 그래서 이번 글은 교안 내용을 따라가되, "이걸 왜 알아야 하지?"라는 질문에 최대한 답이 되게 정리해보려고 한다.

## 이번 주차에서 꼭 잡고 가야 할 질문

이번 2주차를 보면서 머릿속에 남겨야 할 질문은 크게 네 가지였다.

- 컴퓨터는 왜 10진수가 아니라 2진수를 사용할까?
- 비트, 바이트, 워드, 파일, 패킷은 각각 무엇을 말할까?
- 숫자와 문자와 색상은 컴퓨터 안에서 어떤 방식으로 저장될까?
- 논리 연산은 왜 하드웨어와 소프트웨어 모두에서 중요할까?

이 질문들에 답이 잡히면, 이번 주차 내용은 단순 계산 문제가 아니라 "컴퓨터가 세상을 읽고 저장하고 판단하는 방식"으로 연결된다.

## 왜 컴퓨터는 10진수가 아니라 2진수를 쓸까

사람은 10개의 손가락에 익숙해서인지 10진수를 자연스럽게 사용한다. 하지만 컴퓨터는 0과 1, 즉 2진수를 쓴다. 교안에서는 전등의 `켜짐/꺼짐` 비유로 설명하고 있었는데, 이 비유가 가장 직관적이었다.

컴퓨터 내부의 전자회로나 반도체는 결국 전기가 흐르느냐 흐르지 않느냐처럼 **두 상태를 안정적으로 구분하는 것**에 강하다. 0부터 9까지 열 가지 상태를 정확히 구분하는 것보다, 0과 1 두 상태만 명확하게 구분하는 편이 훨씬 단순하고 오류도 적다. 그래서 컴퓨터 입장에서는 2진수가 불편한 방식이 아니라, 오히려 가장 자연스러운 방식이다.

이 부분을 이해하면 "컴퓨터가 왜 모든 걸 숫자로 바꾸는가"도 자연스럽게 이어진다. 문자, 사진, 영상, 음악, 색상까지 겉보기에는 완전히 다른 데이터처럼 보여도, 컴퓨터 안에서는 결국 전기적 신호의 조합으로 표현되어야 한다. 그리고 그 가장 기본 단위가 0과 1이다.

프론트엔드 관점에서도 이 감각은 꽤 중요하다. 우리가 화면에서 다루는 이미지는 압축된 바이너리 데이터고, 문자열은 문자 코드의 나열이며, 색상도 결국 숫자 조합이다. 겉으로는 "디자인"과 "기획"과 "UI" 이야기처럼 보여도, 밑바닥에서는 전부 디지털 정보 표현 규칙을 따른다.

## 비트, 바이트, 워드, 파일, 패킷은 각각 무슨 뜻일까

이번 주차에서 특히 다시 정리하게 된 건 단위였다. 자주 보지만 막상 설명하려고 하면 헷갈리는 단어들 말이다.

### 비트와 바이트

- `bit`는 컴퓨터가 사용하는 데이터의 최소 단위다.
- `byte`는 8bit를 묶은 단위다.

비트는 0 또는 1 하나를 표현하는 단위이고, 바이트는 그 비트 8개를 묶은 단위다. 왜 8개를 묶느냐고 물으면 사실상 컴퓨터 시스템이 오랫동안 그 단위를 기본으로 삼아 왔기 때문이다. 문자 하나를 저장하거나 데이터를 다룰 때 바이트가 기본 단위처럼 쓰이는 경우가 많다.

예를 들어 영문자 하나가 1바이트로 저장되는 경우도 있고, 더 큰 숫자나 한글처럼 복잡한 문자는 여러 바이트를 쓰기도 한다.

### 워드

`word`는 CPU가 한 번에 처리할 수 있는 데이터 크기와 관련된 단위다. 교안에서는 32비트 CPU와 64비트 CPU의 워드를 비교하는 그림이 나왔는데, 이걸 보고 나니 워드는 저장 단위라기보다 **처리 단위**에 더 가깝게 느껴졌다.

즉 비트와 바이트가 "표현과 저장"의 감각이라면, 워드는 "한 번에 얼마나 읽고 계산할 수 있느냐"의 감각에 가깝다.

### 파일과 패킷

- `file`은 데이터가 모여 저장되는 단위다.
- `packet`은 네트워크에서 다루는 일정 크기의 데이터 묶음이다.

여기서 재미있는 건, 같은 데이터라도 맥락에 따라 다르게 불린다는 점이다. SSD나 하드디스크에 저장되어 있으면 파일이고, 네트워크를 통해 이동하는 중이라면 패킷 단위로 쪼개질 수 있다.

프론트엔드 실무에서도 이 차이는 꽤 중요하다. 이미지를 최적화할 때는 파일 크기를 보고, 스트리밍이나 API 성능 이슈를 볼 때는 패킷과 네트워크 전송량을 의식하게 된다. 결국 "데이터"라는 하나의 말 안에 저장, 처리, 전송이라는 서로 다른 층위가 들어 있다.

## 용량 단위는 왜 이렇게 헷갈릴까

교안에서는 `B`, `KB`, `MB`, `GB`, `TB`, `PB` 같은 용량 단위를 표로 정리해두고 있었다. 이 부분은 그냥 외우는 걸 넘어서 한 번쯤 정확히 이해해둘 필요가 있다.

보통 이렇게 올라간다.

- `1KB = 2^10 byte = 1024 byte`
- `1MB = 2^20 byte`
- `1GB = 2^30 byte`
- `1TB = 2^40 byte`

그런데 일상에서는 "1KB = 1000byte"처럼 느껴지는 경우도 있다. 저장장치 제조사 표기와 운영체제 표기가 다르게 느껴지는 이유도 여기서 나온다. 컴퓨터 내부 계산은 2진수 기반이라 `1024`를 기준으로 보는 경우가 많고, 마케팅 표기는 10진수 기준으로 단순하게 쓰는 경우가 있기 때문이다.

이 차이를 알고 있으면 파일 크기나 디스크 용량 표기를 볼 때 덜 헷갈린다.

실무적으로도 꽤 중요하다. 예를 들어:

- 빌드 결과물이 `3MB` 늘었다는 건 실제 번들 크기 변화와 직결된다.
- 이미지 업로드 제한이 `10MB`라면 사용자가 올릴 수 있는 파일 기준이 된다.
- 동영상 리소스를 다룰 때는 캐싱 전략과 로딩 UX까지 함께 영향을 받는다.

즉 용량 단위는 저장 공간에 대한 이야기이면서, 동시에 사용자 경험의 속도와도 연결된다.

## 속도 단위는 용량 단위와 완전히 다른 이야기다

이번 주차에서 꽤 좋았던 건 속도 단위를 따로 정리한 부분이었다. `Hz`, `bps`, `rpm`은 같은 "속도"처럼 보이지만 전혀 다른 상황에서 쓰인다.

### 클록, 클록 틱, 헤르츠

- `클록(clock)`은 일정한 박자를 만들어내는 장치다.
- `클록 틱(clock tick)`은 그 박자 하나를 뜻한다.
- `헤르츠(Hz)`는 1초 동안 클록 틱이 몇 번 발생하는지를 나타낸다.

즉 `2Hz`라면 1초에 두 번 반복되는 셈이다. CPU 성능, 모니터 주사율, 전기 신호 주기 등 다양한 곳에서 이 개념이 등장한다.

### bps

`bps(bit per second)`는 1초 동안 몇 비트를 전송하는지를 나타내는 단위다. 이름이 비슷하다고 해서 바이트와 혼동하면 안 된다.

예를 들어:

- 파일 크기: `10MB`
- 전송 속도: `10Mbps`

이 둘은 같은 `M`이 붙어 있어도 같은 단위가 아니다. 하나는 바이트고 하나는 비트다. 그래서 다운로드 시간을 계산할 때 감으로만 보면 자꾸 체감과 어긋난다.

프론트엔드 개발자로서는 이걸 자주 체감한다. 사용자는 "왜 이렇게 늦게 떠요?"라고 말하지만, 실제로는 이미지 용량, 요청 수, 네트워크 속도, 압축 여부, 캐시 정책이 모두 얽혀 있다. 결국 단위를 이해하는 건 병목을 이해하는 출발점이다.

### rpm

`rpm`은 1분 동안 몇 번 회전하는지를 뜻한다. 하드디스크처럼 회전 기반 저장장치의 성능을 말할 때 자주 나온다. 지금은 SSD가 익숙해서 체감이 덜하지만, 저장장치가 물리적으로 회전하던 시대에는 꽤 직접적인 성능 지표였다.

## 2진수와 10진수 변환은 계산보다 구조를 읽는 일이다

처음 진법 변환을 배우면 너무 시험 문제처럼 느껴진다. 그런데 이번에 다시 보니 그 핵심은 계산보다 **자릿값 구조를 이해하는 것**에 있었다.

예를 들어 2진수 `11101101`을 보자.

오른쪽부터 각 자리는 다음 의미를 가진다.

```text
1*2^7 + 1*2^6 + 1*2^5 + 0*2^4 + 1*2^3 + 1*2^2 + 0*2^1 + 1*2^0
= 128 + 64 + 32 + 0 + 8 + 4 + 0 + 1
= 237
```

즉 2진수는 단순히 1과 0이 나열된 문자열이 아니라, "각 자릿값을 포함할지 말지"를 표시하는 구조다.

반대로 10진수 `237`을 2진수로 바꿀 때는 2로 계속 나누고 나머지를 거꾸로 읽는다.

```text
237 / 2 = 118 ... 1
118 / 2 = 59  ... 0
59  / 2 = 29  ... 1
29  / 2 = 14  ... 1
14  / 2 = 7   ... 0
7   / 2 = 3   ... 1
3   / 2 = 1   ... 1
1   / 2 = 0   ... 1
```

그래서 결과는 `11101101`이 된다.

프론트엔드에서 이걸 직접 손으로 계산하는 일은 많지 않다. 하지만 비트 플래그, 권한 마스크, 압축 포맷, 색상 값, 바이너리 프로토콜 같은 곳에서는 결국 이 사고방식이 필요하다. "이 값은 몇 번째 비트가 켜져 있느냐"를 읽는 감각이 생기면 생각보다 많은 게 연결된다.

## 16진수는 이론보다 훨씬 실무에 가까운 숫자다

이번 2주차에서 제일 반가운 건 역시 16진수였다. 이유는 단순하다. 프론트엔드 개발자는 16진수를 꽤 자주 본다.

가장 대표적인 예가 CSS 색상 코드다.

- `#FFFFFF`는 흰색
- `#000000`는 검정색
- `#FF0000`는 빨간색

교안에서도 16진수 활용 예시로 RGB 색상 표현이 나왔는데, 이 부분은 실무와 정말 딱 맞닿아 있었다.

RGB는 각각 `0~255` 범위를 가지는 값이고, 이를 16진수 두 자리씩으로 표현하면 우리가 익숙하게 보는 색상 코드가 된다.

예를 들어:

- 빨강 `255, 0, 0` -> `#FF0000`
- 파랑 `0, 0, 255` -> `#0000FF`
- 흰색 `255, 255, 255` -> `#FFFFFF`

여기서 핵심은 16진수가 2진수를 사람이 조금 더 읽기 쉽게 압축한 표현이라는 점이다. 2진수 4비트를 16진수 1자리로 표현할 수 있어서, 긴 2진수 값을 더 간단하게 적을 수 있다.

예를 들어 10진수 `237`은:

- 2진수로 `11101101`
- 16진수로 `ED`

가 된다.

즉 `#1A73E8` 같은 색상 코드도 그냥 디자인 툴에서 복붙하는 값이 아니라, 2진 표현과 연결된 디지털 정보의 요약본이라고 볼 수 있다. 이걸 알고 나면 16진수가 괜히 덜 낯설어진다.

## 숫자는 저장 방식에 따라 의미가 달라진다

교안 후반에서는 정수와 실수의 표현 방식도 다뤘다. 이 부분이 중요한 이유는, 사람이 보는 숫자와 컴퓨터가 저장하는 숫자가 항상 같은 방식이 아니기 때문이다.

### 부호 없는 정수와 부호 있는 정수

정수를 저장할 때 가장 단순한 방식은 `unsigned`, 즉 부호 없는 정수다. 모든 비트를 순수하게 크기 표현에 사용하므로 `0`부터 큰 양수만 저장할 수 있다.

하지만 현실에서는 음수도 다뤄야 하니, 부호를 표현하는 방식이 필요하다. 그래서 1의 보수, 2의 보수 같은 표현 방식이 등장한다.

교안에서도 `unsigned`, `1의 보수`, `2의 보수`를 비교하고 있었는데, 여기서 핵심은 2의 보수가 실제 컴퓨터에서 널리 쓰이는 이유다. 덧셈 회로를 단순하게 유지하면서 음수 표현까지 가능하기 때문이다.

쉽게 말해, 컴퓨터는 음수를 그냥 "-" 기호로 저장하지 않는다. 비트 패턴 자체를 다르게 해석해서 음수를 표현한다.

### 오버플로우와 언더플로우

정수 표현 방식에는 범위 한계가 있다. 예를 들어 8비트로 표현 가능한 범위를 넘어서는 값을 넣으려고 하면 오버플로우가 발생할 수 있다. 교안에서도 이 부분을 예시로 보여줬다.

이건 단순 계산 실수가 아니라, **표현 가능한 범위를 넘어간 결과**다.

실무에서는 언어가 알아서 막아주거나, 더 큰 타입을 쓰거나, 런타임이 다르게 처리하는 경우가 많지만, 결국 "숫자는 무한정 큰 게 아니다"라는 기본 전제를 잊으면 안 된다.

## 실수는 왜 정확해 보이는데 자꾸 오차가 생길까

실수 파트도 꽤 중요했다. 교안에서는 고정 소수점과 부동 소수점 개념, 그리고 `float`, `double` 같은 표현 방식을 설명하고 있었다.

실수는 정수보다 훨씬 까다롭다. 소수점을 어디에 둘지, 가수부와 지수부를 어떻게 나눌지, 얼마나 정밀하게 표현할지를 함께 고려해야 하기 때문이다.

이 때문에 컴퓨터에서 실수 계산은 사람이 기대하는 십진수 계산과 정확히 일치하지 않을 때가 있다.

프론트엔드 개발자라면 이걸 정말 자주 본다.

```js
0.1 + 0.2 // 0.30000000000000004
```

이 문제는 JavaScript만의 문제가 아니라, 부동소수점 표현 전반의 문제다. 그러니까 "이 언어가 이상해서"가 아니라 "컴퓨터가 실수를 저장하는 방식이 원래 그렇다"는 걸 이해하는 편이 더 맞다.

가격 계산, 차트 데이터, 퍼센트 표시, 소수점 반올림 같은 UI 작업에서 자꾸 오차 이슈가 생기는 것도 이 배경을 알고 보면 덜 당황스럽다.

## 문자는 감성적인 데이터가 아니라 코드다

문자 표현 파트도 흥미로웠다. 교안에서는 ASCII와 Unicode를 함께 보여주고 있었다.

우리는 문자라고 하면 그냥 "글자"라고 느끼지만, 컴퓨터는 문자를 그대로 저장하지 않는다. 각 문자에 숫자 코드를 대응시켜 저장한다.

### ASCII

영문 중심의 문자 코드 체계다. 초창기 컴퓨터에서 널리 쓰였고, 알파벳과 숫자, 일부 기호를 표현하는 데 적합했다.

### Unicode

전 세계의 다양한 문자를 표현하기 위한 체계다. 한글, 한자, 이모지까지 포함해 훨씬 넓은 범위를 다룬다.

프론트엔드 실무에서 이게 중요한 이유는 명확하다. 인코딩을 잘못 다루면 바로 글자가 깨진다. 한글이 `????`처럼 보이거나, 특수문자가 깨지거나, 서버와 클라이언트가 서로 다른 인코딩을 가정해 버그가 나는 경험은 생각보다 흔하다.

즉 문자는 그냥 사람이 읽는 정보가 아니라, 정확한 코드 체계를 전제로 한 데이터다.

## 논리 연산은 조건문보다 더 밑바닥의 문법이다

후반부에 나온 논리 연산과 논리 게이트는 처음 보면 하드웨어 이야기처럼 느껴질 수 있다. 그런데 사실은 소프트웨어에서도 매일 쓰고 있는 개념이다.

### 기본 논리 연산

- `AND`: 둘 다 참이어야 참
- `OR`: 둘 중 하나만 참이어도 참
- `NOT`: 참/거짓을 뒤집음
- `XOR`: 둘이 다를 때만 참

조건문을 쓸 때 이 논리를 계속 사용한다.

예를 들어:

- 로그인했고 권한도 있어야 버튼을 보여준다. -> `AND`
- 폼 값이 비어 있거나 형식이 틀리면 에러를 띄운다. -> `OR`
- 비활성 상태가 아니라면 실행한다. -> `NOT`

즉 UI 로직도 결국 논리 연산의 조합이다.

### 시프트 연산

교안에서는 좌/우 시프트도 함께 다뤘다. 비트를 왼쪽이나 오른쪽으로 밀어내는 연산인데, 2진수 표현을 직접 다룰 때 자주 등장한다.

- 왼쪽 시프트는 값을 2배씩 키우는 효과가 있고
- 오른쪽 시프트는 값을 2로 나누는 효과와 비슷하다

물론 현대 프론트엔드에서 시프트 연산을 자주 쓰는 편은 아니지만, 비트 연산 API나 저수준 데이터 처리, 그래픽 연산 쪽에서는 여전히 유효하다.

### 논리 게이트

교안의 자동차 경고등 예시가 특히 이해하기 쉬웠다.

- 문 1이 열리거나 문 2가 열리면 경고 -> `OR 게이트`
- 엔진 작동 중이면서 안전 조건을 만족해야 특정 동작 수행 -> `AND 게이트`

이걸 보고 나니 컴퓨터의 판단은 결국 물리적인 전기 회로와 소프트웨어의 조건문이 같은 논리를 다른 층위에서 사용하고 있다는 생각이 들었다. 그 점이 꽤 인상적이었다.

## 이번 주차를 프론트엔드 개발자 관점에서 다시 보면

이번 2주차 내용을 정리하면서 가장 크게 느낀 건, 디지털 정보 표현은 절대 옛날 이론이 아니라는 점이었다. 오히려 지금도 프론트엔드에서 아주 가까운 곳에서 계속 작동하고 있다.

예를 들면 이런 식이다.

- `#RRGGBB` 색상 코드는 16진수 표현을 그대로 사용한다.
- 이미지와 영상 최적화는 바이트 단위의 용량 감각이 필요하다.
- 웹 성능은 `Mbps`, 요청 크기, 캐시 전략과 이어진다.
- 문자열 깨짐 문제는 문자 코드와 인코딩 이해가 필요하다.
- 숫자 계산 버그는 부동소수점 표현 문제와 닿아 있다.
- 조건부 렌더링과 폼 검증은 논리 연산의 조합이다.

결국 화면은 겉으로는 아름답고 추상적이지만, 그 아래는 철저하게 수와 코드와 비트의 세계다.

## 2주차를 정리하며

이번 2주차를 한 문장으로 정리하면 이렇다.

**디지털 정보 표현은 컴퓨터가 세상을 읽는 문법이다.**

2진수와 16진수, 비트와 바이트, 정수와 실수, 문자 코드, 논리 연산은 전부 따로 떨어진 계산 문제가 아니라 컴퓨터가 데이터를 저장하고 처리하고 전송하고 판단하는 방식 전체를 설명하는 규칙이었다.

특히 프론트엔드 개발자로서 이번 내용을 다시 보니 더 와닿았다. 색상 코드 하나, 파일 크기 하나, 네트워크 속도 하나, 문자열 하나도 그냥 감으로 다루는 게 아니라 그 아래의 표현 원리를 이해할수록 더 정확하게 다룰 수 있기 때문이다.

예전에는 2진수나 16진수를 너무 교과서적인 지식처럼 느꼈는데, 이번 주차를 정리하고 나니 생각이 꽤 달라졌다. 이건 오래된 개념이 아니라, 지금도 내가 매일 만지는 웹 화면 뒤에서 계속 작동하고 있는 현재진행형의 언어에 가깝다. 그래서 이번 내용은 "기초"라기보다, 오히려 실무를 더 탄탄하게 이해하게 해주는 바닥 지식이라고 보는 게 더 맞는 것 같다.
