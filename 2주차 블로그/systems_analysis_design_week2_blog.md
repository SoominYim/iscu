# [시스템분석및설계] 시스템분석및설계 학습 (2) - 왜 개발은 코딩 전에 절반이 결정될까?

실무에서 가장 답답한 순간 중 하나는 이런 때다.

화면은 이미 만들어지고 있는데, 요구사항 문서는 애매하고, 누구는 이 기능을 A라고 부르고 누구는 B라고 부르고, 디자이너가 말하는 흐름과 개발자가 이해한 흐름이 조금씩 다르다. 코드는 분명 열심히 쓰고 있는데 이상하게 계속 되돌아간다.

이번 2주차 시스템분석및설계를 보면서 든 생각은, 이런 문제의 상당수는 코딩 실력보다 앞단의 정리 부족에서 나온다는 점이었다. 이번 주차는 프로세스와 산출물, 구조적 방법론과 정보공학 방법론, 객체지향 방법론, 논리적 설계와 물리적 설계, As-Is와 To-Be, EA, UML과 DFD 같은 다이어그램까지 아주 폭넓게 다뤘다.

처음엔 문서 이야기처럼 보일 수 있다. 그런데 끝까지 보고 나면 오히려 이 과목은 **개발이 왜 자꾸 엇나가는지 설명해주는 과목**에 더 가깝다. 그리고 현업 프론트엔드 개발자 입장에서 보면 더더욱 그렇다. 화면은 가장 마지막에 보이는 결과물일 뿐이고, 그 이전에 무슨 문제를 풀지, 어떤 흐름을 만들지, 어떤 데이터를 보여줄지, 어떤 단계로 협업할지가 흔들리면 UI도 결국 계속 흔들리기 때문이다.

## 이번 주차를 읽을 때 붙잡고 가면 좋은 질문

2주차 내용을 보면서 계속 머릿속에 남겨둔 질문은 다음과 같았다.

- 왜 회사마다 개발 단계 이름이 조금씩 다를까?
- 산출물은 왜 필요한가?
- 프로세스와 방법론은 어떻게 다를까?
- 분석과 설계는 어디서 갈리고, 왜 둘 다 필요한가?
- 다이어그램은 왜 아직도 중요한가?

이 질문에 답이 생기면, 교안에 나온 용어들이 형식적인 문서 단어가 아니라 실제 프로젝트를 덜 꼬이게 만드는 장치로 보이기 시작한다.

## 같은 개발인데 왜 회사마다 말이 다를까

교안 초반에서 가장 먼저 짚은 게 바로 이 부분이었다. 모두가 비슷한 폭포수 흐름을 쓴다고 해도, 각 조직은 개발 단계의 이름과 범위를 조금씩 다르게 부를 수 있다는 점이다.

예를 들면 이런 식이다.

- 어떤 회사는 요구 분석을 기획과 요구 정의로 쪼갠다.
- 어떤 회사는 기본 설계라는 말 안에 요구 분석 일부를 포함한다.
- 어떤 회사는 설계와 코딩을 전부 "개발"로 부른다.
- 어떤 회사는 단위 테스트를 구현 안에 포함하고, 어떤 회사는 테스트 단계로 뺀다.

이게 왜 중요하냐면, 용어가 다르면 결국 사람들이 같은 일을 하면서도 다른 그림을 그리게 되기 때문이다.

실무에서도 이 감각은 정말 익숙하다.

- 어떤 팀은 기획서를 요구사항 문서처럼 쓰고
- 어떤 팀은 스토리보드 안에 화면 명세와 API 요구까지 전부 넣고
- 어떤 팀은 와이어프레임만 있어도 설계가 끝났다고 느낀다

결국 중요한 건 용어 자체보다 **팀 안에서 모두가 같은 뜻으로 쓰고 있는가**다. 교안이 작업 절차와 명칭의 통일을 기본 중 기본이라고 설명한 이유가 여기 있다.

## 산출물은 형식주의가 아니라 협업의 기준점이다

2주차에서 특히 인상 깊었던 건 개발 단계별 산출물 설명이었다. 개발 계획서, 요구 분석서, 기본 설계서, 상세 설계서, 코드, 테스트 결과물처럼 단계마다 왜 문서화된 결과가 필요한지 차근히 짚어주는 흐름이었다.

예전에는 솔직히 산출물이라는 단어를 들으면 약간 피로감부터 왔다. "문서가 많다고 프로젝트가 좋아지는 건 아니잖아"라는 생각도 자주 했다. 그런데 이번 교안을 보고 나니 산출물은 문서 그 자체보다 **같은 프로젝트를 보는 공통 좌표계**에 더 가깝게 느껴졌다.

### 개발 계획서

프로젝트의 목적, 일정, 예산, 인력, 리스크 관리 등을 정리하는 문서다. 말 그대로 "우리가 지금 무엇을 위해 이 프로젝트를 하는가"를 팀 단위로 합의하는 문서다.

### 요구 분석서

현재 어떤 문제가 있고, 왜 해결해야 하고, 시스템이 무엇을 해야 하는지를 정리한다. 교안에서도 문제 정의와 시스템 제안의 흐름을 분리해서 설명하고 있었는데, 이 부분이 꽤 좋았다. 문제를 정확히 보지 못하면 해결책도 자꾸 어긋나기 때문이다.

### 기본 설계서

시스템의 큰 구조를 잡는 문서다. 아키텍처, 주요 기능, 데이터 흐름, 주요 모듈 같은 큰 그림이 여기에 들어간다. 말하자면 "무엇을 어떤 덩어리로 나눠 구현할 것인가"를 정하는 단계다.

### 상세 설계서

기본 설계를 실제 구현 가능한 수준으로 구체화한 문서다. 데이터베이스 설계, 인터페이스 명세, 알고리즘, 세부 흐름 등이 들어간다.

프론트엔드 입장에서 이걸 다시 읽어보면 훨씬 현실적이다.

- 사용자 시나리오가 없으면 화면 전환 흐름이 흔들린다.
- API 명세가 없으면 상태 처리와 에러 처리가 흔들린다.
- UI 설계서가 부실하면 개발자가 제각각 해석하게 된다.

즉 산출물은 코딩을 늦추는 종이뭉치가 아니라, **나중에 발생할 재작업을 줄이는 안전장치**다.

## 프로세스와 방법론은 왜 구분해야 할까

교안에서 특히 좋았던 설명은 프로세스와 방법론을 분리해서 본 부분이었다.

- `프로세스`는 무엇을 해야 하는지, 어떤 순서로 가야 하는지를 정한다.
- `방법론`은 그 일을 실제로 어떻게 수행할지를 정한다.

이 차이를 모르고 있으면 개발 이야기가 자꾸 섞인다. 예를 들어 "우린 애자일이야", "우린 객체지향이야", "우린 스프린트로 해" 같은 말들이 전부 한 층위의 말처럼 들리기 쉽다. 그런데 사실은 서로 다른 레벨의 이야기다.

프론트엔드로 치면 이렇게 이해하는 게 편했다.

- 프로세스는 요구 분석 -> 설계 -> 구현 -> 테스트처럼 흐름을 말한다.
- 방법론은 유즈 케이스를 쓸지, DFD를 그릴지, 데이터 중심으로 볼지, 클래스 중심으로 볼지를 말한다.

이 구분을 해두면 프로젝트 대화가 훨씬 정리된다.

## 구조적 방법론은 기능과 흐름을 먼저 본다

교안에서는 구조적 방법론을 기능과 프로세스 중심의 방법론으로 설명했다. 핵심 도구는 `DFD`, `구조도`, `소단위 명세서`였다.

구조적 방법론의 장점은 복잡한 기능을 계층적으로 나누고, 데이터가 어떻게 흐르는지 시각적으로 설명하기 좋다는 점이다. 기능을 분해하고, 그 기능 사이에서 어떤 데이터가 오가는지 보고, 그걸 토대로 구조를 설계한다.

### DFD

`Data Flow Diagram`은 처리 과정과 데이터 흐름을 그리는 도구다. 어떤 입력이 들어와 어떤 과정을 거쳐 어떤 결과로 나가는지를 그릴 수 있다.

프론트엔드에서도 이 사고방식은 꽤 많이 쓰인다. 예를 들어 주문 프로세스를 생각해보면:

- 사용자가 상품을 장바구니에 담는다
- 결제 수단을 선택한다
- 재고를 확인한다
- 주문서를 생성한다
- 결제 완료 상태를 갱신한다

이 흐름은 UI 화면만 봐서는 다 보이지 않는다. DFD나 유사한 다이어그램으로 정리해두면 데이터가 어디서 들어오고 어디서 바뀌는지 훨씬 명확해진다.

### 구조도

구조도는 모듈 간 호출 관계와 계층 구조를 보여준다. 즉 기능을 실제 소프트웨어 구조로 옮겨가는 데 도움이 된다.

이건 프론트엔드에서 컴포넌트 구조와 훅, 서비스 레이어를 어떻게 나눌지 고민하는 것과도 닮아 있다. 문제를 어떤 단위로 나눌지 정하지 않으면 구현은 금방 얽힌다.

## 정보공학 방법론은 데이터와 비즈니스 중심으로 본다

교안에서는 정보공학 방법론을 기업의 전략과 비즈니스, 데이터 중심 설계와 연결해서 설명하고 있었다. 구조적 방법론이 기능과 흐름을 잘게 나누는 데 강하다면, 정보공학 방법론은 기업 전체의 정보와 데이터를 중심으로 시스템을 바라보는 느낌이 강하다.

이 흐름에서 핵심은 다음과 같았다.

- 전략적 시스템 계획 중심
- 데이터 중심 설계
- 비즈니스 문제를 위에서 아래로 분할
- 기업 전체 관점에서 시스템을 바라봄

이 부분은 실무에서도 굉장히 현실적이다. UI는 자주 바뀐다. 버튼 위치, 페이지 구성, 마이크로카피, 라우팅 흐름도 계속 달라진다. 그런데 사용자, 주문, 상품, 결제, 권한 같은 핵심 데이터는 상대적으로 오래 간다.

그래서 프론트엔드가 화면만 보면 안 된다는 생각이 다시 들었다. 어떤 화면이든 결국 핵심 데이터를 다른 방식으로 표현하는 경우가 많기 때문이다. 교안에서 논리 ERD, 비즈니스 프로세스 구조도, 스토리보드, UI 설계서를 함께 언급한 것도 이런 맥락으로 읽혔다.

## 객체지향 방법론은 현실 세계를 더 닮게 만든다

객체지향 방법론 파트도 흥미로웠다. 기능만 따로, 데이터만 따로 보는 대신, 속성과 동작을 함께 가진 객체를 중심으로 시스템을 모델링하는 방식이다.

교안에서는 텔레비전 예시를 들어 설명했는데 꽤 직관적이었다.

- 텔레비전은 채널, 볼륨, 전원 상태를 가진다
- 채널 변경, 볼륨 조절, 켜기/끄기 같은 행동을 한다

즉 객체지향은 "기능"만 보는 것도 아니고, "데이터"만 보는 것도 아니라, 현실의 대상을 하나의 의미 단위로 프로그램 안에 옮기는 방식이다.

프론트엔드에서도 이 감각은 유효하다. 컴포넌트를 봐도 결국:

- 어떤 상태를 가지고
- 어떤 동작을 수행하고
- 어떤 인터페이스로 외부와 연결되는지

를 함께 보게 된다. 물론 React 컴포넌트를 곧바로 객체지향이라고 부르긴 어렵지만, 책임을 묶고 재사용 가능한 단위로 나눈다는 점에서는 연결되는 부분이 꽤 많다.

## 세 방법론은 결국 무엇을 중심에 두느냐의 차이였다

교안 후반에서는 구조적 방법론, 정보공학 방법론, 객체지향 방법론을 비교하고 있었다. 이 비교가 꽤 정리가 잘 됐다.

- 구조적 방법론: 기능과 로직 중심
- 정보공학 방법론: 데이터와 기업 정보 중심
- 객체지향 방법론: 객체와 클래스 중심

결국 같은 시스템을 보더라도 **어떤 관점으로 분해하느냐**가 다르다는 뜻이다. 그래서 프로젝트 성격에 따라 선호되는 방법도 달라질 수 있다.

예를 들어:

- 절차와 흐름이 명확한 시스템은 구조적 접근이 이해하기 쉬울 수 있고
- 기업 전반의 데이터 통합이 중요한 시스템은 정보공학 접근이 강할 수 있고
- 확장성과 재사용성이 중요한 시스템은 객체지향 접근이 더 자연스러울 수 있다

이걸 보고 나니 "정답 방법론"이 있는 게 아니라, 문제 성격에 따라 더 잘 맞는 시선이 다를 뿐이라는 생각이 들었다.

## 논리적 설계와 물리적 설계를 섞으면 왜 위험할까

개인적으로 이번 주차에서 가장 좋았던 구분은 `논리적 설계`와 `물리적 설계`였다.

- 논리적 설계는 시스템이 무엇을 해야 하는지, 어떤 입력과 출력과 처리 흐름이 필요한지를 정의한다.
- 물리적 설계는 그것을 실제 시스템에서 어떻게 구현할지를 구체화한다.

이 차이는 실무에서 진짜 중요하다.

예를 들어 고객 관리 시스템을 만든다고 해보자.

### 논리적 설계에서 보는 것

- 어떤 고객 정보를 받아야 하는가
- 고객 목록은 어떤 기준으로 조회되는가
- 어떤 보고서가 생성되어야 하는가
- 어떤 사용자 권한이 필요한가

### 물리적 설계에서 보는 것

- 화면은 어떤 컴포넌트 구조로 나눌 것인가
- API는 어떤 엔드포인트를 호출할 것인가
- 데이터는 어떤 테이블 구조로 저장할 것인가
- 검색 결과는 어떤 정렬 기준으로 보여줄 것인가

문제는 이 둘이 섞일 때다. 아직 요구도 선명하지 않은데 구현 기술부터 정하면 방향이 자꾸 바뀌고, 반대로 구현 수준의 구체화 없이 요구만 나열하면 실제 개발 단계에서 해석 차이가 커진다.

프론트엔드에서 흔히 "일단 화면부터 만들자"가 위험해지는 이유도 여기 있다. 논리적 설계가 정리되지 않았는데 물리적 설계부터 들어가면 나중에 구조를 다시 뜯는 일이 정말 많아진다.

## As-Is와 To-Be를 나누지 않으면 개선이 아니라 착각이 된다

교안에서 설명한 `As-Is`와 `To-Be`도 굉장히 실무적이었다.

- `As-Is`는 현재 업무나 시스템이 돌아가는 방식
- `To-Be`는 새 시스템이 도입된 이후 목표 상태

이걸 나누지 않으면, 개선 프로젝트가 사실상 현재 문제를 그대로 옮기는 작업이 되기 쉽다.

예를 들어 기존 관리자 페이지가 느리고, 버튼이 많고, 승인 절차가 복잡해서 사용자 불만이 많다고 해보자. 이 상태를 정확히 분석하지 않고 겉보기 디자인만 새로 바꾸면, 결국 예쁜 껍데기만 생기고 문제는 그대로 남는다.

프론트엔드에서도 이건 UX 개선 프로젝트에서 정말 자주 느낀다.

- 현재 사용자는 어디서 멈추는가
- 어떤 단계에서 실수가 많이 발생하는가
- 클릭 수가 왜 많은가
- 어떤 데이터가 불필요하게 중복 입력되는가

이걸 먼저 알아야 To-Be가 의미를 가진다. 결국 To-Be는 상상으로 그리는 미래가 아니라, As-Is를 정확히 읽은 뒤에 나오는 개선안이어야 한다.

## EA는 왜 "큰 그림"에서 자주 등장할까

교안에서는 EA, 즉 엔터프라이즈 아키텍처도 짚고 있었다. 처음에는 조금 거창하게 느껴질 수 있지만, 쉽게 말하면 조직의 전략과 업무, 정보, 기술을 한눈에 볼 수 있게 정리하는 큰 그림에 가깝다.

왜 이 개념이 중요하냐면, 시스템은 단독으로 존재하지 않기 때문이다.

- 조직의 목표와 연결되어야 하고
- 부서 간 업무 흐름과 연결되어야 하고
- 데이터와 기술 구조가 맞물려야 한다

프론트엔드도 예외가 아니다. 화면 하나를 아무리 잘 만들어도, 그 화면이 조직의 업무 흐름과 충돌하면 결국 유지되지 못한다. 그래서 EA는 개발자의 일상 언어는 아닐 수 있어도, 시스템이 어떤 큰 구조 안에서 놓여 있는지 이해하는 데 중요한 관점처럼 느껴졌다.

## 다이어그램은 글보다 게으른 도구가 아니라 더 정직한 도구다

후반부에서는 UML, 업무 흐름도, 순서도, DFD 같은 다이어그램을 다뤘다. 예전엔 다이어그램을 약간 형식적인 산출물처럼 느낀 적도 있었는데, 이번에는 생각이 좀 달라졌다.

다이어그램의 장점은 예쁘게 정리된다는 데만 있지 않다. 오히려 **빠진 관계와 애매한 흐름이 눈에 띄게 드러난다**는 점이 더 중요하다.

### UML

교안에서는 UML을 정적 다이어그램과 동적 다이어그램 관점으로 설명하고 있었다.

- 클래스 다이어그램: 구조와 관계를 표현
- 시퀀스 다이어그램: 시간 흐름에 따른 메시지 교환 표현
- 유즈 케이스 다이어그램: 사용자와 시스템 기능 관계 표현

프론트엔드 관점으로 치면:

- 클래스 다이어그램은 상태와 구조의 관점
- 시퀀스 다이어그램은 API 호출과 사용자 액션 흐름
- 유즈 케이스는 사용자 요구와 기능 맵

같은 감각으로 읽을 수 있었다.

### 업무 흐름도

As-Is와 To-Be를 표현하는 데 특히 유용하다. 실제 업무가 어떤 순서로 흘러가는지, 어느 지점에서 승인이나 분기나 병목이 생기는지를 보여준다.

이건 실제 화면 설계 전에 꼭 필요한 도구처럼 느껴졌다. 왜냐하면 화면은 업무 흐름을 시각화한 결과물이기 때문이다.

### 순서도

처리 절차를 단계별로 보여주는 가장 기본적인 방식이다. 알고리즘 설명에도 좋고, 간단한 업무 절차 설명에도 좋다.

### DFD

데이터가 어디서 오고 어디로 가는지 보여주는 데 강하다. 교안에서도 업무나 시스템의 데이터 흐름을 명확히 하는 데 적합하다고 설명하고 있었다.

프론트엔드 개발자로서는 API 요청과 응답, 사용자 입력과 서버 저장, 캐시와 화면 상태 변화를 정리할 때 비슷한 사고방식이 계속 필요하다고 느꼈다.

## 결국 개발은 코딩 전에 이미 많이 결정된다

이번 2주차를 보면서 계속 든 생각은 이거였다.

개발은 에디터를 열기 전에 이미 절반 이상이 결정된다.

- 용어가 통일되어 있는지
- 산출물이 적절한 수준으로 정리되어 있는지
- 어떤 방법론으로 문제를 볼지 합의했는지
- 논리적 설계와 물리적 설계가 분리되어 있는지
- As-Is와 To-Be가 정리되어 있는지
- 다이어그램으로 흐름이 보이는지

이 중 몇 가지만 흔들려도 뒤에서 구현을 아무리 열심히 해도 계속 돌아오게 된다.

프론트엔드 쪽은 특히 "보이는 결과"가 빨리 나오다 보니, 분석과 설계보다 일단 화면부터 만들고 싶어질 때가 많다. 그런데 실제로는 그럴수록 재작업이 늘어난다. 이번 주차는 그 불편한 사실을 아주 차분하게 설명해주는 시간이었다.

## 2주차를 정리하며

이번 2주차 시스템분석및설계는 문서를 잘 쓰는 법을 배우는 시간이 아니라, 개발을 덜 헷갈리게 만드는 법을 배우는 시간에 가까웠다.

프로세스와 산출물, 구조적/정보공학/객체지향 방법론, 논리적 설계와 물리적 설계, As-Is와 To-Be, EA, UML과 DFD 같은 다이어그램은 전부 다른 주제처럼 보이지만 결국 하나의 방향을 향하고 있었다.

**같은 대상을 같은 언어와 같은 수준으로 이해하자.**

프론트엔드 개발자로 일하면서 이 메시지가 특히 크게 다가왔다. 화면은 가장 마지막에 보이는 결과물이지만, 그 앞단의 분석과 설계가 흐리면 구현은 계속 흔들린다. 반대로 앞단이 선명하면 구현은 오히려 훨씬 빨라진다.

예전에는 시스템분석및설계가 코딩에서 조금 떨어진 과목처럼 느껴졌는데, 이번 주차를 정리하고 나니 오히려 개발을 더 현실적으로 바라보게 만드는 과목이라는 생각이 든다. 잘 만든 화면은 예쁜 화면이 아니라, 앞단에서 충분히 이해된 시스템 위에 올라간 화면이라는 것도 이번 주차를 통해 다시 선명해졌다.
